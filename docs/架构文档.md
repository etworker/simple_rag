## 1. 总体架构

simple_rag 采用**分层模块化**架构，按职责划分为 4 个独立 Python 包，依赖方向严格单向、无循环：

```
┌─────────────────────────────────────────────────────────────┐
│                         rag_server                             │
│                  (FastAPI 应用 / 编排层)                      │
│   路由(routes): documents · qa · review                      │
│   服务(services): doc_store · parse_cache · qa_engine ·      │
│                review_runner · chat · config_store · ...     │
└───────────────┬───────────────────────────┬─────────────────┘
                │ 依赖                        │ 依赖
                ▼                            ▼
        ┌──────────────────┐        ┌──────────────────┐
        │   version_diff   │────────│    doc_parser    │
        │  (差异检测引擎)   │        │   (文档解析)      │
        └────────┬─────────┘        └──────────────────┘
                 │ 依赖
                 ▼
        ┌──────────────────┐
        │     llm_chat     │
        │ (LLM 调用抽象)    │
        └──────────────────┘
```

### 依赖方向（无环）

```
doc_parser  ─┐
             ├─► version_diff ─► rag_server
llm_chat   ─┘        │
                     └─► rag_server
```

- `doc_parser`、`llm_chat` 为**叶子依赖**，不依赖其他业务模块。
- `version_diff` 依赖 `doc_parser`（解析）与 `llm_chat`（判定/归纳）。
- `rag_server` 依赖其余三者，是唯一的"应用编排层"。

> 约束：生产代码无 `sys.path` hack；测试为隔离会临时注入路径。依赖通过 **uv workspace** 管理——仓库根 `pyproject.toml` 声明 `members`（doc_parser / llm_chat / version_diff / rag_server），各模块 `pyproject.toml` 的 `[tool.uv.sources]` 用 `{ workspace = true }` 引用兄弟包，根级 `uv.lock` 统一锁版本，`uv sync --project rag_server` 后即按正式包名导入，无需任何路径 hack。

## 2. 模块职责

| 模块 | 路径 | 职责 | 关键公共 API |
|------|------|------|--------------|
| **doc_parser** | `doc_parser/src/doc_parser/` | 文档解析（PDF/Word）→ 段落 + 表格 + 定位；PDF 多后端（auto 默认路由 / pdfplumber / pymupdf / docling / mineru） | `parse(filepath, config)`；`Paragraph`/`Table`/`Document` |
| **llm_chat** | `llm_chat/src/llm_chat/` | LLM 调用抽象（bedrock / openai 等多后端）、重试、会话 | `ask_once(prompt, backend, ...)`；`ChatSession` |
| **version_diff** | `version_diff/src/version_diff/` | 差异检测引擎：语义配对 + 字级 diff + 规则预过滤 + LLM 判定 + 版本对比 + 冲突检测 | `DiffEngine`、`Config`、`judge_pairs`、`detect_conflicts`、`call_llm_json` |
| **rag_server** | `rag_server/app/` | FastAPI 应用：上传、预审核编排、RAG 问答、冲突检测、Web UI | `app/main.py` + `app/routes/*` + `app/services/*` |

## 3. 技术栈

| 层 | 技术 |
|----|------|
| Web 框架 | FastAPI + Uvicorn，SSE 进度推送 |
| 文档解析 | auto 默认路由；pdfplumber（稳定文本段落）、pymupdf（快路径）、python-docx（Word）、MinerU（VLM/OCR/扫描件）、Docling（TableFormer 表格/无框线表） |
| 向量检索 | **fastembed（ONNX Runtime）+ 进程内 FAISS `IndexFlatIP`（当前 CPU）**；Embedding 可在 CPU 或 T4 上运行 |
| Embedding 设备 | `embedding.device=auto` 可使 fastembed/ONNX 选择 GPU（快速原型可选 T4）；这与 FAISS 是否使用 GPU 无关，Windows 等环境可保持 embedding GPU + FAISS CPU |
| Embedding 模型 | `BAAI/bge-small-zh-v1.5`（本地缓存，离线可用；零 torch 依赖） |
| LLM 后端 | Amazon Bedrock（`bedrock_converse`，在可用区域）、OpenAI 兼容（`openai`，含远端或本地 GLM / DeepSeek）；中国区自建 `GLM-4.7-Flash` 时由 A10G + vLLM 提供端点 |
| 深度解析引擎 torch | CUDA 版（有 GPU）/ CPU 版（无 GPU，mineru pipeline 可跑） |
| 持久化 | 文件系统（解析缓存、向量缓存、页面缓存、上传目录、config.json） |
| 任务编排 | asyncio 后台任务 + 进度回调（非消息队列） |
| 依赖管理 | `uv` **workspace**（根 pyproject.toml 声明 4 模块成员 + 根 uv.lock） |
| 测试 | `pytest`（每模块独立套件，共用根 `.venv`） |

## 4. 核心数据流

### 4.1 预审核流（新文档入库前）

```
用户上传 ─► rag_server/upload
   │
   ├─ 同名不同内容？── 是 ─► 返回 needs_choice（coexist / new_primary；overwrite 兼容）
   │
   ▼
写入上传目录（SHA256 命名，原子写）
   │
   ▼
review_runner.run_pre_review(task_id)  [asyncio 后台]
   │
   ├─ 1. parse_cache.cached_parse（文件哈希+解析配置命中则跳过解析）
   ├─ 2. 加载向量模型，取得当前 active 文档列表
   ├─ 3. 对每篇已有文档计算整篇相似度并排序
   ├─ 4. 逐文档比较（结果渐进推送）
   │       ├─ 相似度 >= version_similarity_threshold
   │       │    └─ version_compare(old, new)：段落/表格版本差异
   │       └─ 其他文档
   │            └─ pre_review(new)：检索 → diff → 规则过滤 → LLM 矛盾判定
   ├─ 5. 任一确定性比较组或其 LLM 判断失败 → 顶层任务 `error/incomplete`，不得判为安全；`parse_qa.incomplete` 是独立旁路，不单独阻止确认
   └─ 6. 完整成功结果写回任务状态，并按文档哈希+有效配置签名写入可复用结果缓存
   │
   ▼
SSE 进度推送 → 前端展示每篇文档的矛盾/变更
   │
   ▼
人工 confirm（入库，`mode=keep_current` / `new_primary`）/ reject（丢弃）
   │
   └─ 确认入库时，有旧主版本的新文档先写为 inactive；`new_primary` 再切换为同族唯一 active/primary，`keep_current` 保留旧主版本；旧版不自动删除
```

### 4.2 问答流（RAG）

```
用户提问 ─► qa.ask(question, session_id)
   │
   ├─ 1. doc_store 检索 top_k 相关段落（相似度阈值过滤）
   ├─ 2. detect_conflicts(retrieved_passages)  [统一冲突检测]
   │       跨文档预过滤 → score/相似度门控 → LLM 确认 → 回退启发式
   ├─ 3. 组织 prompt（检索内容 + 系统提示 + 冲突警告）
   ├─ 4. ask_once(...) 生成答案（带 [1][2] 引用）
   ├─ 5. 前端按 sources.idx 显示每条证据；同一文档可有多个引用项
   ├─ 6. 若存在冲突，在答案中注入 ⚠️ 冲突提示
   └─ 7. 返回 {answer, sources, conflicts, has_conflicts}
```

## 5. 部署拓扑

```
[ 浏览器 / 客户端 ]
        │  HTTP / SSE
        ▼
[ rag_server (FastAPI, :8000) ]
        │                  │
        │ 调用             │ 调用
        ▼                  ▼
[ version_diff ]      [ doc_parser ]
        │
        ▼
[ llm_chat ] ──► [ LLM 后端: 可用区域 Bedrock / OpenAI-compatible / 中国区 A10G 自建 GLM ]
        ▲
        │
[ 本地 Embedding (bge via fastembed) + FAISS 向量库（文件缓存） ]

本地文件系统：
  ~/.simple_rag/
    ├─ uploads/        上传文件（SHA256 命名）
    ├─ parse_cache/    解析结果缓存
    ├─ vector_cache/   向量缓存
    ├─ page_cache/     PDF 页面 PNG 缓存
    ├─ review_tasks.json  终态预审核任务状态快照
    └─ review_results/    完整且可复用的预审核结果缓存
  <repo>/rag_server/config.json   运行配置（不入库）
```

- 启动：`start.sh`（Linux/macOS）/ `start.bat`（Windows）→ `uv sync` → 加载 `.env` → `uvicorn app.main:app --port 8000`。
- 安装：推荐根级 `python setup_env.py`，自动检测 CPU/NVIDIA GPU 并选择互斥的 `cpu`/`gpu` extra；Linux GPU 可使用 Faiss GPU，Windows GPU 使用 Faiss CPU。
- 离线：设置 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1` 避免 HuggingFace 联网。
- 无独立数据库；文档元数据、解析/向量/页面/审核缓存和会话历史使用本地文件系统。预审核任务、当前运行状态和未完成结果主要在进程内存中；服务重启不能可靠恢复未完成任务。任务状态可以写入状态快照，但按文档哈希和有效配置签名的 review result cache 只缓存完整成功结果。

### 5.1 当前本地运行态与目标云架构边界

> **部署分档**：快速原型可部署在单台普通 CPU 机器上，完成解析、Embedding、FAISS、版本审核和 RAG 问答；需要缩短 Embedding/Docling/MinerU 耗时时，可选 T4 GPU。A10G 不是普通原型的默认硬件，仅在 AWS 中国区无法使用 Bedrock、需要自建 `GLM-4.7-Flash` 时，用于运行 vLLM/OpenAI-compatible LLM 服务。CPU/T4 原型仍可连接可用区域的 Bedrock 或其他 OpenAI-compatible 端点。

上面的拓扑是当前可运行的本地/单进程拓扑：本地文件系统、进程内 `IndexFlatIP`、fastembed/ONNX 和 FastAPI。OpenSearch、DynamoDB、Aurora、Keycloak、S3、Secrets Manager 等只在 [快速原型部署方案](快速原型部署方案.md) 中作为目标适配方案，当前代码未接入，不能作为现状依赖或恢复能力的承诺。
- 审核报告当前只有 `GET /api/documents/review/{task_id}/report.html` 生成的单文件 HTML，不应推断存在 PDF/JSON/CSV；报告当前不渲染 `suspects`。
- `parse_qa` 默认关闭，是解析质量旁路，不替代 compare/conflict；清空知识库不删除 chat history、logs 或上传目录。
- 预审核只逐个比较当前 `active` 文档；QA 在全量 FAISS 搜索后按 active 状态过滤 inactive。

## 6. 组件交互（rag_server 内部）

```
app/main.py
  ├─ app/routes/documents.py   文档列表/预览/删除/清空
  ├─ app/routes/qa.py          问答/会话管理/来源查询
  ├─ app/routes/review.py      上传/预审核/确认/拒绝/重跑/进度SSE
  └─ app/services/
        ├─ config_store.py     ConfigStore（运行时配置）
        ├─ doc_store.py        文档元数据 + 段落/向量落盘
        ├─ parse_cache.py      解析结果缓存（to_dict/from_dict）
        ├─ qa_engine.py        RAG 问答 + 冲突检测委托
        ├─ review_runner.py    预审核编排（3 个 helper）
        ├─ chat.py / chat_history.py  会话与历史
        └─ page_renderer.py    PDF 页面渲染（PNG）
```

依赖规则：`routes` 只调用 `services` 与 `app.routes._state`；`services` 调用下层包（`version_diff`/`doc_parser`/`llm_chat`）。
