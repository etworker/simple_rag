# 从 PDF 解析到版本对比：文档入库与 RAG 问答的实现原理

> 面向非技术读者的公开技术科普文章
>
> **当前基线说明**：本文以当前工作区代码、`rag_server/config.example.json` 和 doc_parser 默认配置为准；开头的提交号只是历史定位信息，不是部署版本承诺。若历史段落与当前路由/服务行为冲突，以代码为准。
>
> **重要说明**：本文描述的是当前系统的实际处理方式，基线为 `main@b653abf`（包含文档版本管理、审核/矛盾检测改进和 embedding 批次进度）。文中使用的文件名、制度名称、数值和内容均为虚构示例，不代表任何真实文档。对于“建议配置”“后续可以增加”等内容，文章会明确标注其当前实现状态。

## 1. 先用一句话理解系统

系统不是把 PDF 文件简单地“上传到一个文件夹”，而是会经过下面这条链路：

```text
上传文件
  ↓
读取 PDF / Word 内容
  ↓
识别段落、标题、表格和页码
  ↓
把内容切成多个可处理的小单元
  ↓
为文本单元生成语义向量（Embedding）
  ↓
与知识库中已有文档做相似度筛选
  ↓
根据情况做版本差异比较或矛盾检测
  ↓
展示审核结果，等待人工确认
  ↓
确认后建立正式的问答检索索引
  ↓
用户提问时检索相关内容，并由 LLM 组织答案
```

可以把它类比成一个文件管理员：

1. **读文件**：先把 PDF 中的文字和表格读出来。
2. **分卡片**：把一整本手册拆成很多张“内容卡片”，每张卡片保留原来的页码和章节位置。
3. **做标签**：为每张卡片生成一个能够表示语义的数字标签。
4. **找相似卡片**：新文档上传时，去已有文档中找可能讲同一件事的卡片。
5. **核对内容**：找到对应卡片后，再逐字或逐单元格检查具体变化。
6. **请人确认**：系统把结果交给人确认，确认后才正式放入问答知识库。

## 2. 先区分几个容易混淆的概念

### 2.1 “上传”不等于“正式入库”

系统把流程分成两个阶段：

- **上传并预审核**：文件保存下来，系统解析文件并检查它与已有文档的关系。
- **确认入库**：用户查看审核结果后，明确点击确认，系统才把内容加入正式问答索引。

这样做的原因是：如果一份新制度还没有经过审核，系统不能让它马上参与问答，否则可能出现以下问题：

- 新文档其实是错误版本，却已经影响问答结果；
- 新文档与旧文档存在矛盾，但用户还没有看到；
- 用户点击上传只是想先预览，并没有授权它进入知识库；
- 覆盖旧版本时，如果中途失败，旧版本不应被破坏。

因此，系统采用“先审核，后提交”的方式，类似代码系统中的 Pull Request：

```text
提交变更
  ↓
自动检查
  ↓
人工查看检查结果
  ↓
批准后合并
```

### 2.2 “段落”不等于“页”，PDF 里的段落也不是天然存在的

Word 文档通常有明确的段落节点；PDF 更像“画布上的文字块”。文字块往往只保存字符、字体和坐标，程序需要根据坐标、行距、标点和版面关系，反推出哪些文字属于同一段。因而本文说的“段落”是解析器重建出来的语义近似，不是 PDF 文件原生提供的字段。

一页可能包含多个段落，一段内容也可能跨越多页。例如：

```text
5.2 数据备份要求
系统管理员应每日执行一次数据备份，备份完成后应检查任务状态，
并将异常情况记录在运维台账中。
```

系统希望把它识别为一个语义完整的段落，而不是简单地按“每页一块”处理。段落通常会保留：文本内容、起始页和结束页、章节编号、章节标题、来源文件和在文档中的位置。

### 2.3 一句话一段怎么办？段落超长怎么办？

**一句话一段并不是错误。** 如果 PDF 或 Word 中一段只有一句完整的话，例如：

```text
系统管理员应每日检查备份任务状态。
```

解析器会把它作为一个完整的 chunk。系统不会为了“凑够字数”强行把它和下一段拼接，因为下一段可能已经属于另一个条款。短段是否保留还会经过最小长度和标题判断；章节标题、列表项等有结构意义的短文本不能简单按字数删除。

**段落很长时会进行二次切分。** 当前规则 PDF 解析默认以约 600 个字符作为普通段落上限，并优先在句号、问号、分号、逗号等自然断点切开；如果长段没有自然标点，达到上限后也会强制断开，避免一个超大 chunk 影响检索。切分时尽量不从词语或半句话中间截断。

可以把它理解为以下规则：

```text
完整短段       → 保留为一个 chunk
一句话短段     → 保留为一个 chunk，不强行拼接
长段且有句号   → 在句末附近切成多个 chunk
长段无断点     → 达到上限后强制切分
章节标题       → 单独作为一个结构块
跨页未完句     → 尽量与下一页合并
```

PDF 还会做跨页合并：只有页面相邻、前段看起来没有结束、不是新标题/表格/列表，并且合并后没有过长时才合并。当前实现的合并上限约为普通上限的两倍。Word 路径则更接近“一个 Word 段落对应一个 Paragraph”，不会把所有段落重新拼成 PDF 式全文流；这也是不同文件格式不能用同一套规则处理的原因。

### 2.4 什么是 chunk

在 RAG 系统里，**chunk** 可以理解为一个可以单独检索的内容单元。当前项目的基本约定是：

```text
普通文字：一个解析后的语义段落 ≈ 一个 chunk
表格：一张表转换成一个结构化文本 chunk
```

这里的“≈”很重要：段落是解析器根据版面和规则重建的，不保证等同于原作者在 Word 中点击回车形成的段落。系统不是简单地每 500 个字切一刀，而是综合参考章节标题、空行、句末标点、段落长度、页面关系、表格区域以及页眉页脚和重复行。

### 2.4 什么是 Embedding

Embedding 可以翻译为“文本向量”或“语义向量”。

它不是把文字翻译成另一种语言，也不是把文字加密，而是把一段文字转换成一串数字。这串数字用于表示文字的语义位置。

例如：

```text
“系统每天执行一次备份”
“每日进行数据备份”
```

两句话用词不同，但意思接近。它们生成的向量通常也会比较接近。

再例如：

```text
“系统每天执行一次备份”
“办公区域应保持整洁”
```

两句话主题差异较大，向量通常会相距较远。

Embedding 的作用不是最终判断两段话是否矛盾，而是帮助系统快速找到“可能在讲同一件事”的内容。

### 2.5 什么是向量检索

向量检索就是：

```text
拿一个内容单元的向量
  ↓
在已有向量中寻找距离最近的几个向量
  ↓
返回最可能相关的内容
```

项目使用 FAISS 作为本地向量检索组件。用户不需要把 FAISS 理解成一个新的数据库，可以先把它理解为“根据向量快速找相似内容的索引”。

### 2.6 什么是 LLM

LLM 是大语言模型。系统使用它做需要理解语言含义的工作，例如：

- 判断“每天”和“每周”是不是实质性差异；
- 判断两段文字只是表达方式不同，还是确实互相矛盾；
- 根据检索出的文档内容生成回答；
- 把多个差异整理成用户容易阅读的摘要。

LLM 不负责替代 PDF 解析，也不负责替代向量检索。它通常是在系统已经找出候选内容之后，进行更高层次的语言判断。

### 2.7 什么是 RAG

RAG 是“检索增强生成”的简称。

普通聊天模型可能只依靠训练时学到的知识回答问题；RAG 会先从用户自己的知识库中检索相关段落，再把这些段落交给 LLM，让 LLM 基于检索结果回答。

简化理解：

```text
用户提问
  ↓
从用户文档中找相关内容
  ↓
把找到的内容交给 LLM
  ↓
LLM 根据这些内容组织答案
```

所以，RAG 的关键不是“让模型记住所有 PDF”，而是“提问时先把相关 PDF 内容找出来”。

## 4. 第一步：上传文件

### 4.1 系统做什么

用户选择一个 PDF 或支持的 Word 文档后，系统会：

1. 读取上传内容；
2. 计算文件 SHA-256 哈希值；
3. 用安全文件名保存上传文件；
4. 创建一个预审核任务；
5. 后台开始执行预审核；
6. 前端通过任务状态或 SSE 进度查看执行情况。

文件哈希可以理解为文件的“指纹”。只要文件内容完全相同，它的哈希通常也完全相同。

### 4.2 为什么不用原始文件名作为内部文件名

原始文件名可能包含：

- 中文和特殊字符；
- 很长的目录信息；
- 重复名称；
- 不同系统不兼容的字符。

因此系统内部通常使用哈希和扩展名保存，例如：

```text
内部保存名：<文件哈希>.pdf
界面显示名：数据备份管理制度.pdf
```

用户看到的业务文件名和系统内部存储文件名可以不同。

### 4.3 重复文件如何处理

#### 情况 A：同名且内容完全相同

系统会提示该文档已经存在，避免重复上传。

#### 情况 B：同名但内容不同

上传接口会先返回选择：

- **保留旧版本并进行版本审核**（`coexist`）：继续审核新文档，确认时使用 `keep_current` 保留旧主版本，或使用 `new_primary` 切换新版本；
- **审核后使用新版本**（`new_primary`）：继续审核并默认倾向在确认时切换新版本。

新文档在上传/审核阶段尚未写入正式文档元数据。确认入库时，有旧主版本的新文档先以 `inactive` 历史版本保存；若确认模式为 `new_primary`，再切换为该文档族唯一的 `active`、`primary` 版本，若为 `keep_current` 则旧版本继续作为当前主版本。旧版本不会因为上传或确认新版本而被删除，仍可在文档管理中查看；只有显式删除文档时才会移除。旧客户端传入的 `overwrite` 仍可兼容，但现在只表示倾向 `new_primary`，不再代表删除旧文件。

#### 情况 C：文件名不同但内容相同

系统通过完整文件哈希识别重复内容。相同内容不会重复入库，即使文件名不同也会拒绝重复记录。

### 4.4 系统会自动选择“最新版本”吗？

当前实现需要区分三个概念：

1. **同名上传的比较对象**：系统按文档族和入库时间找到当前 `active` 文档，作为同名上传的比较对象；
2. **版本识别**：系统按整体相似度排序，并且同名文档即使相似度较低也会进入版本差异分支；
3. **问答时的生效版本**：同一文档族通过 `primary` 机制保持唯一 `active` 版本，问答默认只检索 active 文档。

因此，系统不会根据版本号或发布日期自动推断业务上的“最新”，但同一文档族也不会默认让旧版和新版同时参与问答。新版本确认时可以选择保留当前主版本（`keep_current`），也可以切换新版本为主版本（`new_primary`）；历史版本转为 `inactive`，仍保留用于查看和比较。

当前还没有按结构化版本号、生效日期或会话范围自动筛选 RAG 的 `rag_scope` 配置。文档的 `version` 字段是兼容保留字段，用户填写的版本号或说明应放在 `label` 中；按版本号排序和按生效日期选择属于后续设计。

建议设计（不是当前可直接使用的配置）可以包括：

```text
latest_by_added_at     → 按入库时间选最新
latest_by_version      → 按结构化版本号选择，如 1.10 > 1.9
latest_by_effective_at → 按生效日期选择
manual                 → 用户在多个版本中指定检索范围
```

可靠支持这些策略还需要保存结构化 `version`、`effective_date`、`supersedes_doc_id` 等字段，并在检索请求中传递范围。当前代码已经支持通过文档管理接口手工切换文档族的主版本，但尚未实现上述自动排序、会话级多版本检索范围。

## 5. 第二步：解析 PDF 或 Word

### 5.1 为什么 PDF 解析比 Word 难

Word 的正文通常以段落、表格、标题等结构写入 OOXML 文档；PDF 更多是在页面上记录“把什么内容画在什么坐标”，并不一定保存“这是第几个段落”这样的语义信息。一个看起来完整的 PDF 页面，底层可能是以下几种情况：

```text
可提取文字 PDF：字符 + 字体 + 坐标
扫描 PDF：整页图片，需要 OCR
表格 PDF：文字块、线条、矩形区域，未必有真实单元格
复杂 PDF：多栏、浮动图形、页眉页脚、脚注、印章、旋转文字
```

表格尤其容易造成误解：人眼看到的是行、列和单元格，但 PDF 里可能只有几条横线、几条竖线和许多分散的文字块；无边框表格甚至只有按坐标排列的文字。解析器需要根据几何位置和文字内容推断表格结构。因此不存在一个对所有 PDF 都完美的解析库。不同解析库在文字顺序、跨页内容、扫描件 OCR、无框线表格和复杂版面上的强项不同，才需要准备多个后端并允许比较、切换和人工抽查。

当前系统会根据文件特征选择或降级到不同解析后端，并在解析后做页眉页脚过滤、段落重建、表格清洗和跨页合并。后端选择提高了适应性，但不能消除 PDF 本身缺少语义结构带来的不确定性。

### 5.2 解析不是简单复制文字

系统需要从文件中尽可能恢复结构：

```text
文件
├── 普通文字
├── 章节标题
├── 段落
├── 表格
├── 页码位置
├── 章节位置
└── 页面关系
```

一份制度文件可能显示为：

```text
第 1 页：标题、目录
第 2 页：第 1 章正文
第 3 页：第 2 章正文和表格
第 4 页：表格续页
```

系统解析后更关心的是：

```text
段落 A：第 2 章 数据备份要求……
段落 B：备份完成后应检查任务状态……
表格 C：备份任务记录表……
```

### 5.2 普通文本段落如何切分

当前系统会尽量按语义切分，而不是完全按固定字数切分。

常见判断信号包括：

1. 章节标题前后；
2. 空行；
3. 句末标点；
4. 段落长度是否达到上限；
5. 页眉页脚和重复行；
6. 跨页文本是否是同一个句子或列表。

例如，下面内容更适合作为一个完整 chunk：

```text
5.2 备份要求
系统管理员应每日执行一次备份。备份完成后，应检查备份任务状态，
发现异常时应在运维台账中登记，并通知值班负责人。
```

如果强行每 50 个字截断，可能变成：

```text
块 1：系统管理员应每日执行一次备份。备份完成后，应检查
块 2：备份任务状态，发现异常时应在运维台账中登记……
```

后者会损失上下文，不利于检索和对比。

### 5.3 表格如何解析

表格会保留为独立的结构化对象，通常包括：

- 表头；
- 行和列；
- 表格所在页码；
- 所属章节；
- 表格前后的上下文。

例如：

| 编号 | 检查项目 | 周期 | 责任部门 |
|---|---|---|---|
| 1 | 数据备份 | 每日 | 信息技术部 |
| 2 | 日志检查 | 每周 | 运维组 |

系统不会只把它当成一张图片，而会尽量识别其中的行列关系。

### 5.4 跨页表格

如果一个表格跨越多页，解析器会尝试：

- 合并连续页面中的同一张表；
- 去除重复表头；
- 保留表格的完整行列关系。

但 PDF 的表格排版非常复杂，以下情况可能影响结果：

- 没有边框的表格；
- 单元格大量合并；
- 扫描件表格；
- 表格文字实际上是图片；
- 页面中存在复杂浮动对象。

因此，表格解析结果仍建议在人工审核页面中抽查。

### 5.5 扫描件 PDF

如果 PDF 只有图片，没有文字层，普通文字提取无法直接得到文本。

这时需要 OCR 或视觉解析能力。系统会根据配置选择合适的解析后端，但扫描质量、倾斜、印章遮挡、低分辨率都会影响结果。

常见现象：

- 解析出的段落数量很少；
- 文字出现乱码；
- 表格行列识别不完整；
- 页码和章节定位不准确。

遇到这种情况，应先检查解析结果，再判断是否需要更换解析后端或重新扫描文件。

---

## 6. 第三步：生成 Embedding

### 6.1 Embedding 解决什么问题

Embedding 主要解决“意思相近的内容如何快速找出来”的问题。

例如，以下内容虽然字面不完全相同，但语义接近：

```text
旧版：系统管理员每天进行一次数据备份。
新版：数据备份的执行频率调整为每日一次。
```

关键词可能不同，但系统希望它们能够被配对。

### 6.2 Embedding 不等于差异结论

Embedding 只能帮助系统找到候选内容，不能单独说明：

- 哪个数字变了；
- 哪个条款被删除了；
- 两段内容是不是矛盾；
- 变化是否符合业务规则。

因此实际流程是：

```text
Embedding：这两段可能在讲同一件事
  ↓
文本 diff：具体哪些文字不同
  ↓
规则过滤：是不是页码、编号、日期等噪声
  ↓
LLM 判断：是不是实质性变化或真正矛盾
```

### 6.3 两类向量用途

系统中存在两个逻辑用途相近、但服务目标不同的向量过程。

#### 用途一：文档对比向量

用于：

- 判断两篇文档整体是否相似；
- 为新旧版本的段落配对；
- 从另一篇文档中找相似段落；
- 为跨文档矛盾检测寻找候选内容。

#### 用途二：RAG 问答向量

用于：

- 用户问题转成向量；
- 在所有已确认文档中寻找相关段落；
- 建立正式的问答检索索引。

两者可能使用同一个 embedding 模型，也可能使用不同的索引和缓存范围。当前系统会尽量复用相同内容、相同配置下已经生成的向量缓存。

### 6.4 空知识库为什么不做文档对比

如果知识库是空的，第一份文档没有旧文档可以比较。

此时系统会：

```text
解析第一份文档
  ↓
确认知识库中没有已有文档
  ↓
跳过跨文档检索和差异判断
  ↓
等待人工确认
  ↓
确认后为 RAG 建立正式向量索引
```

这不是漏掉了对比，而是没有比较对象。

### 6.5 向量缓存

Embedding 计算可能比较耗时，尤其是大 PDF。因此系统会缓存结果。

通常缓存会与以下信息有关：

- 文件内容；
- 解析后的段落数量和内容；
- embedding 模型；
- 相关配置。

如果文件和配置没有变化，重新运行时可以直接读取缓存，避免重复计算。

如果更换 embedding 模型，旧向量不能简单视为兼容，通常需要重新建立知识库索引。

### 6.6 Embedding 批次进度和缓存事件

当前向量计算支持可选的批次进度回调。事件包含：

```text
phase/status/completed/total/batch_index/batch_total/pct/cached
```

状态通常包括：

- `running`：正在按批计算；默认批次大小为 64；
- `done`：某一批或全部内容计算完成；
- `cached`：命中向量缓存，没有重新计算；
- `empty`：没有可向量化的段落。

预审核流程会把这些事件包装为文档编号、文档总数、文档名和 `stage_pct`，通过审核任务的 SSE `details` / `embedding_progress` 推送到页面。它表示向量计算阶段的进度，不等于整个审核流程的百分比；解析、比较和 LLM 判断仍有各自的阶段。确认入库时会复用缓存，但当前没有把同样的批次回调完整接入确认阶段的 SSE，因此不能据此承诺确认阶段也展示同样的细粒度进度。

---

## 7. 第四步：判断新文档属于哪种情况

当知识库中已有文档时，系统会先对新文档和每一篇已有文档做相似度筛选。

流程可以理解为：

```text
新文档
  ↓
依次与已有文档比较整体相似度
  ↓
得到候选排序
  ↓
每篇文档分别进入比较分支
```

系统不会把整个知识库粗暴地合并成一篇超大文档，也不会默认所有不同文档互相矛盾。

通常会分成两类：

```text
同名，或整体相似度达到 version_similarity_threshold
  → 更像同一制度的不同版本
  → 走版本差异比较

文件名不同且相似度低于阈值
  → 更像不同来源的制度或规定
  → 走跨文档矛盾检测
```

系统先按整体相似度从高到低排序，再逐个生成 `compare_groups`。同名是强制的版本信号：即使大幅改版导致相似度低，也不会被误分到跨文档矛盾检测。每个比较组独立记录 `compare_type`、状态、差异、矛盾和疑似项；任意组失败都会使整项预审核变为不完整，不能直接确认“安全”。

这里的阈值是配置项，不是一个永远适用于所有行业的绝对标准。相似度高也不一定证明两份文档就是正式版本关系，最终仍需要人工确认。

---

## 8. 第五步 A：同一文档新旧版本的对比

下面用一个简单例子说明。

### 8.1 旧版内容

```text
5.2 数据备份要求
系统管理员应每天执行一次数据备份。
备份保留期限为 30 天。
```

### 8.2 新版内容

```text
5.2 数据备份要求
系统管理员应每周执行一次数据备份。
备份保留期限为 90 天。
```

### 8.3 段落配对

系统先判断两段话是否在讲同一件事：

```text
旧段落：系统管理员应每天执行一次数据备份。
新段落：系统管理员应每周执行一次数据备份。
```

两段的主题和结构相近，因此可能被配成一对。

配对过程大致是：

1. 完全相同的文本优先直接配对；
2. 其余段落生成 embedding；
3. 使用向量索引寻找另一篇文档中最相似的候选；
4. 每段最多配对一个目标段落；
5. 相似度不足的内容可能被判定为新增或删除。

### 8.4 文本差异

配对之后，系统再做文字级比较：

```diff
- 系统管理员应每天执行一次数据备份。
+ 系统管理员应每周执行一次数据备份。
```

Embedding 负责“找到对应段落”，真正指出“每天变成每周”的是文本 diff。

### 8.6 “元数据噪声”具体指什么？版本变化算不算？

这里的“噪声”不是“所有版本变化”，而是指**不改变制度业务含义、但经常随排版或文档管理自动变化的内容**，例如：

```text
修订日期：2025-01-01 → 2025-02-01
文档版本：V1.0 → V1.1
页码跟踪：第 12 页 → 第 13 页
修订记录表中的更新时间、修订人、流水号
目录或有效页清单中的页码变化
纯空格、换行、标点格式变化
仅条款编号变化，正文含义不变
```

**版本号变化本身通常属于元数据噪声，但版本号所代表的正文变化不是噪声。** 例如：

```text
版本：V1.0 → V1.1                         → 通常归入元数据
备份周期：每天 → 每周                      → 实质性变化
修订记录：增加“调整备份周期”的一行          → 记录行可归入跟踪噪声，但正文变化必须保留
```

当前过滤逻辑默认开启噪声过滤：对修订日期、版本戳、跟踪表行、纯空白和部分编号变化进行规则分类；带单位的数值变化，例如“30 天 → 90 天”“每日 → 每周”，默认保留为实质性候选，不会因为它看起来像版本变化就自动忽略。无法通过规则确定的变化再交给 LLM；LLM 失败时倾向保守保留。

### 8.7 灵敏度能否配置？

可以调节，但当前实现是多个阈值和开关的组合，还不是一个统一的 `sensitivity=low/medium/high` 参数。主要配置方向包括：

| 目标 | 调节方式 | 影响 |
|---|---|---|
| 是否启用噪声过滤 | `diff.noise_filter.enabled` | 关闭后，日期、版本戳等也作为普通差异保留 |
| 哪些行算跟踪表噪声 | `tracking_table.hints`、`row_patterns` | 控制修订记录、有效页清单等的分类 |
| 哪些字符串算版本戳 | `version_stamp_patterns`、`noise_filter.patterns` | 控制日期、版本号、页码等剥离范围 |
| 段落是否能配对 | `diff.similarity_threshold` | 越低越容易配对，也越可能错配 |
| 版本整体分流 | `pre_review.version_similarity_threshold` | 越低越容易按版本处理，越可能把不同文档误认为版本 |
| 改写段落二次配对 | `rewrite_pair_threshold` | 越低越容易合并改写，也越可能误合并 |

如果需要“最灵敏、任何风吹草动都列出来”，当前可采用以下策略：

```text
关闭 noise_filter；
清空或收紧 tracking_table 的噪声规则；
让版本号、日期、页码变化不再被剥离；
降低或关闭仅编号/纯格式差异的归类；
保留所有 added、removed、modified，并把 minor_changes 也展示出来。
```

这样会列出更多变化，包括日期、页码、版本号、空白和解析边界变化，误报也会明显增加。反过来，默认模式忽略常见元数据噪声，但不忽略明确的业务数值和条款增删。若希望用户在页面上直接选择“默认/敏感/最敏感”，需要在现有多个配置项之上新增一个统一预设映射，目前还没有单独的 UI 灵敏度按钮。

### 8.8 LLM 在版本对比中的作用

版本对比不是把所有差异都交给 LLM。当前流程大致是分层处理：

1. 先进行精确/语义段落配对，并对表格按表头、列、行和单元格比较；
2. 对 `added`、`removed` 和明确的实质性变化保留确定性结果；
3. 规则过滤修订日期、版本戳、跟踪表、空白、部分编号变化等常见噪声；
4. 只有剩余的不确定 `modified` 差异才交给版本过滤 LLM，判断保留、忽略或生成摘要；
5. LLM 调用失败时倾向保守保留差异，而不是当作没有变化。

例如：

```text
变化 1：第 3 页页码格式变化       → 规则可能归入细微变化
变化 2：备份周期由每天改为每周     → 明确保留为实质性候选
变化 3：责任部门名称发生改写       → 可能交给 LLM 或人工确认
```

版本过滤使用随包的版本过滤提示词；`judge.prompt_file` / `prompt_template` 主要用于跨文档 consistency judge 和 QA 冲突检测，不能混为同一个配置。LLM 的判断结果仍然只是审核辅助，不替代业务负责人最终确认。

## 9. 第五步 B：表格版本差异比较与 RAG 表示

版本对比和 RAG 检索都使用表格，但目的不同：版本对比要回答“哪一行哪一列改了什么”，RAG 要回答“这张表是否与问题相关”。因此两条路径会使用同一份解析结果，却采用不同的表示方式。

### 9.1 原始表格示例

旧版：

| 编号 | 检查项目 | 周期 | 责任部门 |
|---|---|---|---|
| 1 | 数据备份 | 每日 | 运维组 |
| 2 | 日志检查 | 每周 | 运维组 |

新版：

| 编号 | 检查项目 | 周期 | 责任部门 |
|---|---|---|---|
| 1 | 数据备份 | 每周 | 运维组 |
| 2 | 日志检查 | 每周 | 安全组 |
| 3 | 权限检查 | 每月 | 安全组 |

### 9.2 版本对比：保留表格结构逐项比较

系统通常按以下方式处理：

1. 根据表头相似度配对新旧表格；
2. 根据列名模糊匹配对齐列；
3. 主要使用首列或稳定的行关键字配对行；
4. 对齐后的单元格内容逐项比较；
5. 检测新增列、删除列、新增行、删除行和修改单元格。

对于上面的例子，结果可能是：

```text
第 1 行“数据备份”：周期 每日 → 每周
第 2 行“日志检查”：责任部门 运维组 → 安全组
第 3 行“权限检查”：整行新增，周期为每月
```

这里的“结构化”不是指把差异交给 LLM 猜，而是先使用表头、列、行和单元格的对应关系定位变化。当前版本对同一文档新旧版本支持表格配对、列增删、行增删、单元格修改和基础跨页表格合并。

### 9.3 RAG 检索：表格会转换成什么？

当前 RAG 入库**不是把表格直接存成 JSON 去做向量化**，也不是把表格截图交给向量模型。解析阶段会先保留表格结构对象，本质上包含 `rows`、可选 `headers`、页码、章节和来源等字段；随后 `DocStore` 调用 `Table.to_markdown()`，将其序列化为一段 Markdown 文本，再作为一个可检索的 Paragraph 计算 embedding。

上面的表格进入 RAG 时，效果类似下面这个文本块：

```markdown
| 编号 | 检查项目 | 周期 | 责任部门 |
| --- | --- | --- | --- |
| 1 | 数据备份 | 每日 | 运维组 |
| 2 | 日志检查 | 每周 | 运维组 |
```

然后这个 Markdown 字符串与普通段落一样生成向量，并加入全局 FAISS 索引。向量索引保存的是数字向量和位置映射，不保存一个可直接查询的 JSON 表格对象；原始表格结构仍保留在解析结果或缓存中，用于版本对比和来源定位。

所以，用户问“日志检查周期是什么”时，检索到的文本块可能就是上面的 Markdown。LLM 看到的是带有表头和列关系的文本，而不是失去列顺序的一串词。

### 9.4 两种表示方式的关系和边界

可以简单记住：

```text
解析阶段：保留表格结构对象
版本对比：继续使用结构对象，按表头/列/行/单元格比较
RAG 检索：结构对象序列化为 Markdown 文本，和普通段落一起向量化
```

两条路径不是使用两套互不相关的内容：它们共享解析结果，但版本对比需要结构，RAG 需要适合语义检索的文本。对于两份独立文档的跨文档冲突检测，当前主要拿检索到的文本块做通用语言判断，并没有同等完整的行列级表格冲突算法。复杂合并单元格、图片表格、表头完全变化或没有稳定行键时，仍应人工复核。

---

## 10. 第五步 C：独立文档的跨文档矛盾检测

并不是所有相似文档都是版本关系。

例如：

```text
《总部数据备份管理办法》：重要系统每日备份。
《分公司数据备份管理细则》：重要系统每周备份。
```

它们可能不是同一文档的 V1/V2，而是不同管理范围下的文件。系统需要尽量把它们视为“可能存在冲突的不同来源”。

### 10.1 大致流程

```text
新文档段落
  ↓
生成 embedding
  ↓
在已有文档中找相似候选段落
  ↓
排除完全相同或仅格式不同的内容
  ↓
进行文本差异分析
  ↓
交给规则和 LLM 判断是否构成真正矛盾
  ↓
输出冲突点和双方说法
```

### 10.2 什么叫真正矛盾

下面是明显矛盾：

```text
文档 A：备份保留 30 天。
文档 B：备份保留 90 天。
```

下面不一定是矛盾：

```text
文档 A：普通系统每日备份。
文档 B：核心系统每小时备份。
```

因为两个文档的适用范围可能不同。

再例如：

```text
文档 A：由信息技术部负责。
文档 B：由信息安全部负责。
```

这可能是矛盾，也可能是两个不同职责层级。系统可以标记为需要关注，但最终应由业务人员结合适用范围判断。

### 10.3 为什么需要 LLM

单纯比较关键词容易误报：

```text
“每月检查一次”
“每季度检查一次”
```

它们确实可能是矛盾。

但以下内容只是不同表达：

```text
“每个自然月至少检查一次”
“每月开展一次检查工作”
```

LLM 可以根据上下文辅助判断两者是否表达同一要求，以及变化是否具有业务意义。

### 10.4 “安全”是什么意思

预审核中的 `safe` 或“可安全入库”不是说文件绝对正确，也不是说文件没有任何文字变化。

它更准确地表示：

- 当前自动比较没有发现需要阻止入库的差异；
- 或者比较任务成功完成且没有检测到问题；
- 仍然需要业务人员对重要文档进行最终确认。

### 10.5 解析质量检查不是矛盾检测

如果配置开启 `parse_qa.enabled`，预审核还会对解析结果做旁路质量检查。它关注的是“内容有没有被正确解析出来”，而不是“两个文档是否互相矛盾”，例如：

- 段落是否疑似截断或重复提取；
- 表格是否错列、缺行或跨页合并异常；
- 是否需要建议更换解析后端或检查某个页码范围。

结果通常包含 `status`、`issues`、`incomplete`，以及可选的 `suggested_backend`、`page_range` 等字段。解析质量检查失败不会修改原始解析缓存；LLM 或配置异常时会保留规则检查结果并标记不完整。`parse_qa.incomplete` 应与跨文档矛盾的 `incomplete` 分开理解，前者提示解析质量需要复核，后者表示比较组没有完整完成。

## 11. 第六步：人工审核和确认

预审核完成后，界面会展示：

- 文档是否解析成功；
- 文档包含多少段落和表格；
- 与哪些已有文档进行了比较；
- 文档整体相似度；
- 版本变化；
- 跨文档矛盾；
- 是否存在比较失败或 LLM 判断失败；
- 相关页码和来源位置。

用户可以：

- 确认入库；
- 拒绝入库；
- 对失败任务重新执行；
- 在支持的流程中暂停或继续预审核。

### 11.1 确认入库时发生什么

确认入库不是再次上传文件，而是把已经通过审核的文件提交到正式知识库：

```text
读取解析缓存
  ↓
准备普通段落和表格文本块
  ↓
生成或复用 RAG embedding
  ↓
加入全局向量检索器
  ↓
保存文档元数据、段落和索引
  ↓
文档正式可用于问答
```

### 11.2 为什么确认时还可能等待

预审核和正式入库的目标不同：

- 预审核重点是“找问题”——使用解析出的普通段落和表格结构，完成整体相似度、段落配对、版本 diff 或冲突候选分析；
- 正式入库重点是“让今后问答能检索”——把确认后的普通段落和表格 Markdown 文本块加入全局 RAG 索引。

两阶段通常**共享同一份解析结果和同一个基础 chunk 边界**，不是预审核按段落、确认入库又重新按完全不同的规则切一遍。差别在于：版本对比保留表格对象做行列比较；RAG 则把表格对象序列化为 Markdown 文本，并把普通段落与表格文本块一起加入向量索引。

一份大文档可能包含几千个普通段落和表格块。确认阶段需要为这些内容建立或复用 RAG 向量索引，CPU 环境下可能需要一段时间。

系统会尽量复用预审核阶段已经计算过的向量缓存，但如果：

- 这是第一份文档，预审核没有旧文档可比较；
- RAG 索引与对比索引的缓存键或内容范围不同；
- embedding 模型或配置发生变化；
- 缓存不存在或已经失效；

确认阶段仍可能重新计算。这里的“chunk 不同”主要是表格的表示方式不同，不是普通文字段落被无理由地重新切分。

### 11.3 同文档版本如何确认

同名新文档不会在上传时直接替换旧文档。确认入库时有两种模式：

```text
保留当前版本（keep_current）
  → 确认时将新文档以 inactive 历史版本保存
  → 旧文档继续是该文档族唯一 active/primary 版本

使用新版本（new_primary）
  → 确认时先将新文档以 inactive 保存，确保旧版本可回滚
  → 入库成功后切换新文档为唯一 active/primary 版本
  → 同族其他版本转为 inactive
```

上传和预审核阶段的新文档尚未写入正式文档元数据。

旧版本不会因版本切换自动删除，仍可在文档列表中查看，也可以通过 `POST /api/documents/primary` 将某个历史版本重新设为当前版本。只有显式删除文档时才会移除文件和索引内容。如果审核失败、用户拒绝或入库失败，原有主版本不会被破坏。

### 11.4 预审核结果如何理解

预审核结果不是只有“安全/不安全”两个状态。每个 `compare_group` 表示新文档与一个库中文档的比较，可能是 `version_diff` 或 `conflict`，并包含独立的状态、差异、矛盾和疑似项。汇总结果还包括：

- `version_changes`：版本差异；
- `minor_changes`：规则识别出的细微变化；
- `inconsistencies`：已确认的跨文档矛盾；
- `suspects`：证据不足或 LLM 置信度不足、需要人工复核的疑似项；
- `n_*` 计数：各类比较组、矛盾、疑似项和错误组数量；
- `incomplete` / `n_error_groups`：比较未完整完成，不能按“无问题”处理；
- `parse_qa`：可选的解析质量检查结果，不等同于内容矛盾检测。

没有确定性矛盾但存在 `suspects` 时，含义是“没有确认的矛盾，但仍需人工复核”，不是“完全安全”。任一比较组失败都会阻止确认入库，修复原因后可使用重跑功能。

### 11.5 当前 HTTP 接口与报告

当前 Web API 的主要入口如下；完整参数以代码和 API 文档为准：

| 能力 | 主要接口 |
|---|---|
| 上传和预审核 | `POST /api/documents/upload`、`GET /api/documents/review/active`、`GET /api/documents/review/{task_id}/progress`（SSE） |
| 审核控制 | `POST /api/documents/review/{task_id}/pause`、`resume`、`cancel`、`rerun`、`confirm`、`reject`、`label` |
| 预览 | `GET /api/documents/review/pdf`、`page`、`old/info`、`old/page` |
| 审核报告 | `GET /api/documents/review/{task_id}/report.html` |
| 文档管理 | `GET /api/documents/list`、`POST /api/documents/primary`、`POST /api/documents/label`、删除和清空接口 |
| 普通问答 | `POST /api/qa/ask`、`POST /api/qa/reset`、`GET /api/qa/sessions`、`GET /api/qa/sessions/{session_id}`、`DELETE /api/qa/sessions`、`DELETE /api/qa/sessions/{session_id}`、`source` / `context` |
| 配置和日志 | `GET/POST /api/config`、`GET /api/config/schema`、日志 tail 和 WebSocket 日志接口 |

审核完成后可以导出一个**单文件 HTML 报告**。它不依赖服务器、脚本、图片或外部网络，包含任务状态、结论、比较组、版本差异、细微变化、跨文档矛盾、表格变化和新旧定位信息；当前报告实现**不渲染 `suspects`**，疑似项应以审核结果 API/UI 为准。目前没有已实现的 PDF、JSON 或 CSV 审核报告导出接口。页面预览接口和离线 HTML 报告是两项不同能力。

## 12. 第七步：用户问答的完整流程

文档确认入库后，用户提问时，系统会执行另一条 RAG 链路。

```text
用户问题
  ↓
直接使用原问题生成 embedding
  ↓
在全局向量索引中搜索候选
  ↓
按来源文档的 active 状态过滤 inactive 历史版本
  ↓
按相似度阈值过滤并保留 top-k
  ↓
检查这些内容之间是否存在跨文档冲突
  ↓
拼接上下文和来源编号
  ↓
调用 LLM 生成答案
  ↓
返回答案、来源和冲突标记
```

当前实现**不会先调用 LLM 润色问题，再把润色结果转 embedding**，也没有查询扩展或多轮问题改写。用户原问题直接送入 embedding 模型；多轮对话历史主要用于答案生成。未来可以增加“查询改写”开关，但那属于新增能力，需要评估改写是否改变原问题含义。

### 12.1 示例

用户提问：

```text
数据备份需要保留多久？
```

系统可能检索出：

```text
[1] 《总部制度》：备份保留 30 天。
[2] 《项目管理细则》：核心系统备份保留 90 天。
```

如果两段内容适用范围不同，系统可以在答案中分别说明；如果它们看起来描述同一个范围但数值不同，系统可能标记冲突，提醒用户不能简单合并理解。

### 12.2 检索范围、top-k 和效率

当前问答的有效范围是状态为 `active` 的文档：不同文件和不同文档族的普通段落、Markdown 表格块共享一个全局向量索引。同一文档族默认只有一个 `active`/`primary` 版本；历史版本为 `inactive`，不会出现在 QA 返回结果中。系统尚未实现按版本号、发布日期或会话选择范围的 `rag_scope` 过滤。

实现上的一个重要边界是：当前 `DocStore.search()` 为了在过滤 inactive 后仍能补足 top-k，会先在全量 FAISS 索引中搜索，再根据段落所属文档的状态过滤。因此 inactive 向量仍会被扫描并占用索引空间，但不会作为问答来源返回。未来可以改为带 metadata filter 的检索索引。

查询向量生成后，检索器返回候选近邻，再丢弃低于 `similarity_threshold` 的结果并保留配置的 `top_k`。当前运行配置通常是 `top_k=15`、相似度阈值 `0.5`；代码无文件默认值可能是 `top_k=5`，具体以部署配置为准。所谓 top-k 不是把所有文档全文交给 LLM，而是先把候选数量限制在一个较小范围，再把这些候选和必要的来源信息放入提示词。

当前使用进程内 FAISS `IndexFlatIP`，归一化向量的内积可近似理解为余弦相似度。它适合中小规模知识库，检索时会扫描索引中的向量；文档新增或删除后通常需要更新或重建索引。embedding 计算、解析和向量缓存可以避免重复工作，但不能改变 Flat 索引随向量数量增长的特性。规模很大时，可以把 Retriever 替换为更适合大规模数据的近似索引或向量数据库，并增加按文档、权限、版本和业务范围的预过滤。

答案中的：

```text
备份保留期限为 30 天 [1]。
```

`[1]` 对应系统返回的来源列表，来源通常包括：

- 文件名；
- 文档编号；
- 页码或章节位置；
- 匹配分数；
- 被检索到的文本片段。

用户可以点击来源，查看原文或页面预览。

### 12.3 上下文扩展

如果一个问题命中了某个段落，系统还可以取该段落前后的相邻段落，帮助 LLM 看到完整语境。

例如：

```text
命中段：备份完成后应检查任务状态。
前一段：系统管理员应每日执行备份。
后一段：发现异常时应记录在运维台账。
```

这样模型不会只看到一句孤立的话。当前 `retrieval.context_radius` 默认值为 2，会把命中段落同文档前后的相邻段落一并带入上下文。追问时，如果新检索结果最高分低于 `retrieval.min_followup_score`（代码默认约 0.45），系统可能不注入新的检索上下文，而主要依赖当前会话历史。

需要区分三类质量检查：普通 `/api/qa/ask` 是面向用户的 RAG 问答；预审核中的 consistency judge 是对跨文档候选做审核判断；可选的 `parse_qa` 只检查解析质量。普通 QA 的冲突检测在 LLM 不可用时可以回退到启发式提示，而预审核比较组在关键 judge 失败时会标记 error/incomplete 并阻止确认入库，两者的失败语义不同。

### 12.4 问答不等于事实证明

问答系统的答案来自当前已入库文档和当前检索结果。

它不能保证：

- 文档本身一定正确；
- 文档没有过期；
- 所有相关文档都被检索到；
- 业务适用范围一定被模型正确理解；
- 不同文档之间的权限和优先级已经自动解决。

对于审批、合规、生产操作等重要场景，应结合来源原文和业务负责人确认。

## 13. “对比 embedding”和“RAG embedding”到底是不是两次

这是用户最容易问的问题之一。

### 13.1 逻辑上是两个用途

```text
对比向量：用于找出新旧文档中可能对应的段落
RAG 向量：用于用户提问时找出相关知识
```

### 13.2 底层内容可能相同

两者都可能使用解析器产生的段落作为基础内容，因此不是“前一次切成一种 chunk，后一次完全重新切成另一种 chunk”。

当前系统更接近：

```text
同一份解析结果
  ├── 对比索引：按文档或文档对建立匹配关系
  └── RAG 索引：把已确认文档汇总成全局检索索引
```

### 13.3 普通段落相同，表格表示不同

普通文字在两条路径中通常都来自同一份解析后的 Paragraph，但 embedding 输入并不只是裸的 `Paragraph.text`：如果存在章节编号或标题，向量化文本会带有类似 `章节：...
正文：...` 的前缀；原始正文、章节和页码字段仍分别保留，用于展示、定位和文本 diff。

```text
PDF/Word 解析结果
  ├── 版本对比：用段落做语义配对，再做文本 diff
  └── RAG 索引：章节前缀 + 段落正文 → embedding
```

表格则是：

```text
解析结果中的 Table
  ├── 版本对比：保留 rows/headers，按表头、列、行、单元格比较
  └── RAG 索引：Table.to_markdown()，并带章节信息 → embedding
```

所以，“确认阶段需要为段落和表格块建立或复用 RAG 向量索引”并不意味着 RAG 阶段采用完全不同的段落切分规则；它表示 RAG 索引要接收两类内容：带章节上下文的普通段落，以及由表格转换而来的 Markdown 文本块。

### 13.4 缓存可以避免重复计算

如果内容、解析结果、模型和配置一致，向量缓存可以被复用。因此“逻辑上有两个用途”不等于“必然完整计算两遍”。

### 13.6 云端模型不可用时，可以使用 7B 以下本地模型吗？

可以从接口层面接入，但要区分“能接通”和“效果足够好”。当前项目的 LLM 接入方式是调用 Bedrock 或 OpenAI-compatible 的聊天接口；项目本身不直接加载本地权重。因此，可以使用 Ollama、vLLM、LM Studio 或其他兼容服务启动一个本地模型，再把配置的 `base_url` 指向它，例如：

```yaml
llm_profiles:
  local_small:
    provider: openai
    base_url: http://127.0.0.1:11434/v1
    model: <本地模型名称>
llm_routing:
  qa: local_small
  pre_review: local_small
  conflict_detection: local_small
```

7B 以下模型可以尝试用于：

- 依据检索内容生成简短问答；
- 对格式简单的差异做摘要；
- 在严格提示词和小批量输入下输出结构化 JSON。

但当前源码没有验证某个具体小模型在中文 PDF、表格差异、跨文档冲突和严格 JSON 输出上的效果，因此不能承诺所有 7B 以下模型都能达到云端模型水平。影响因素包括量化方式、上下文窗口、显存或内存、并发能力、模型是否擅长中文和指令遵循。

比较稳妥的本地化方案是：Embedding 继续使用本地 fastembed/ONNX 模型；LLM 通过本地 OpenAI-compatible 服务提供；版本差异中的数值变化和明显增删尽量由规则直接识别，把小模型用于摘要和有限判断；对无法可靠输出 JSON 的情况保守标记为需要人工审核，而不是当成“没有差异”。如果完全没有 LLM，仍可运行解析、向量检索和基础文本/表格 diff，但依赖语言理解的冲突判断和自然语言答案质量会下降。

## 14. 常见用户问题 FAQ

### Q1：上传后文档是不是马上就能问答？

不是。上传后先进入预审核，只有用户确认入库后才会参与问答。

这是为了避免未经审核的内容立即影响知识库。

### Q2：为什么上传以后还要点击一次确认？

确认是一个人工审批门。系统可以自动发现差异，但不能替业务负责人决定“是否允许这份文档正式生效”。

### Q3：为什么空知识库中的第一份文档没有矛盾结果？

因为没有旧文档可以比较。它仍然会解析、切分，并在确认后建立 RAG 索引，但不会凭空产生跨文档矛盾。

### Q4：为什么确认入库时还需要等待？

确认阶段需要为文档的段落和表格块建立或复用 RAG 向量索引。文档越长、内容单元越多、使用 CPU 越慢，等待时间越长。

### Q5：上传阶段是不是应该把所有事情都做完，确认时立即完成？

从用户体验角度，这是可以优化的方向。当前系统为了把预审核和正式提交分开，确认时仍可能建立 RAG 索引。

后续可以让预审核阶段提前生成并缓存 RAG embedding，确认时直接提交缓存索引，以减少确认等待时间。

### Q6：Embedding 能不能直接判断“每天”和“每周”是矛盾？

不能单独依靠 embedding 判断。

Embedding 负责找到可能对应的段落；文字 diff 和 LLM 才负责进一步判断具体变化和业务含义。

### Q7：如果两段话只是换了说法，会不会被误报？

有可能被列为候选差异，但系统会通过文本归一化、规则过滤和 LLM 判断减少误报。最终仍建议人工查看原文。

### Q8：如果只改了页码、日期或版本号，会不会被认为是重大变化？

系统包含针对常见元数据噪声的过滤逻辑，但 PDF 排版差异复杂，不能保证所有情况都自动过滤。审核页面仍可能展示少量细微变化。

### Q9：同名文档一定会被当成版本吗？

同名是强制的版本信号：同名新文档会进入版本差异流程，即使整体相似度低；不同文件名的文档则按相似度阈值决定走版本差异还是跨文档矛盾检测。用户仍需在审核后确认是否让新文档成为当前主版本。

### Q10：选择使用新版本后，旧文档会立刻被删除吗？

不会。新文档确认时先以 `inactive` 保存，成功后才切换为该文档族唯一的 `active`/`primary` 版本；旧版本转为 `inactive` 并保留。审核失败、拒绝或入库失败时，旧版本继续作为当前版本。只有显式删除操作才会移除文档。

### Q11：选择保留当前版本有什么意义？

`keep_current` 适合以下情况：

- 新版本需要先保留并继续人工评估；
- 新旧版本需要互相对照，但当前问答仍使用旧主版本；
- 暂时不能确定新版本是否已经生效。

此时新文档会保存为 inactive 历史版本，不会进入默认 QA 结果；之后可以通过文档管理接口手工切换 primary。

### Q12：系统会把知识库中的每篇文档都拿来比较吗？

新文档会依次与已有文档进行相似度评估和比较。文档数量很多时，预审核耗时会增加。

系统先做相似度排序，再优先处理最可能相关的文档；但当前流程仍可能需要检查多个已有文档。

### Q13：版本对比是不是把每个段落和所有段落全部两两比较？

不是简单的全量两两比较。

通常流程是：

1. 先生成向量；
2. 用 FAISS 找每个段落的 top-K 近邻；
3. 按相似度和一对一规则配对；
4. 对配对结果做文字 diff。

这样比完整两两比较更快。

### Q14：表格会不会被忽略？

版本对比中不会完全忽略表格。表格会通过表头、列、行和单元格进行独立比较。

但独立文档的跨文档矛盾检测目前主要针对普通段落，表格矛盾的自动检测覆盖不如版本表格比较完整。

### Q15：表格中的数字变化能发现吗？

在表格成功解析并且表格能够正确配对的情况下，可以发现单元格内容修改，例如：

```text
30 天 → 90 天
```

但如果表格是图片、表头变化很大、列合并复杂或第一列无法稳定标识行，准确率可能下降。

### Q16：扫描版 PDF 能处理吗？

可以尝试，但需要 OCR 或视觉解析能力。扫描质量越差，解析结果越可能受到影响。上传后应重点检查：

- 文字是否正确；
- 表格是否完整；
- 页码和章节位置是否正确。

### Q17：为什么 PDF 页面上看起来是文字，系统却解析不出来？

有些 PDF 实际上是图片，或者文字被保存为不可正常提取的图形对象。人眼能看到，不代表程序能直接读取文本。

### Q18：系统会把完整 PDF 直接交给 LLM 吗？

通常不会把整份 PDF 原始文件直接当作一个整体交给 LLM。系统会先解析和筛选，只把与差异判断或问答相关的候选文本、差异内容和必要上下文发送给 LLM。

具体发送内容取决于审核分支、配置和 LLM 提示词设置。涉及敏感文件时，应结合部署网络、数据合规和 LLM 服务区域进行评估。

### Q19：Embedding 模型和 LLM 是一回事吗？

不是。

- Embedding 模型：把文字变成向量，用于相似度检索；
- LLM：理解文字、判断差异、生成答案。

它们可以由不同的模型和不同的硬件运行。

### Q20：更换 Embedding 模型后，旧文档还能继续使用吗？

不建议直接混用。不同模型产生的向量维度和语义空间可能不同。切换模型后通常需要重建知识库向量索引，必要时重新上传或重新入库文档。

### Q21：CPU 和 GPU 有什么区别？

主要影响速度，不改变业务流程：

- CPU：部署简单，适合小规模文档，Embedding 速度较慢；
- GPU：适合大批量或大文档，Embedding 通常更快；
- LLM 如果使用云端 Bedrock，则由云端模型完成，和本地 embedding 的 CPU/GPU 是两个不同环节。

### Q22：文档已经解析过了，为什么还会看到“解析”日志？

系统使用解析缓存。日志中的“解析完成”可能表示：

- 第一次真正解析；
- 从缓存恢复了解析结果；
- 配置变化导致缓存失效后重新解析；
- 入库阶段重新读取同一解析缓存。

需要结合日志中的“命中缓存”或“重新执行”信息判断是否真的重复计算。

### Q23：预审核失败后可以怎么办？

通常可以：

1. 查看错误阶段；
2. 检查文件是否完整；
3. 检查 embedding 模型是否可用；
4. 检查 LLM 凭证、网络和模型配置；
5. 使用重新审核功能；
6. 必要时更换解析后端。

预审核失败时不应把结果直接当作“安全”。

### Q24：LLM 不可用时能否继续入库？

取决于具体分支和配置。对于需要 LLM 判断的矛盾或实质性变更过滤，如果判断没有完成，系统应将审核标记为不完整或失败，而不是伪装成“没有问题”。

### Q25：没有发现矛盾，是否就说明文档绝对正确？

不是。

“没有发现矛盾”只表示当前解析、检索、规则和 LLM 判断链路没有识别出问题。它不能证明：

- 文档内容符合现实；
- 文档是最新版本；
- 文档适用于当前业务范围；
- 所有隐藏在扫描图片或复杂表格中的内容都已识别；
- 不存在系统没有检索到的矛盾。

### Q26：为什么同一事实在不同文档中没有被合并成一个答案？

因为不同文档可能代表不同部门、区域、时间或适用范围。系统会保留来源，并在发现冲突时提示用户，而不是擅自决定哪个文档一定正确。

### Q27：如果文档内容一样但文件名不同，会重复入库吗？

系统会依据文件哈希和文档元数据进行处理。具体是否允许不同文件名并存，需要结合业务规则确认。原则上应避免把同一内容作为多份独立制度重复加入。

### Q28：删除文档后，向量会不会还留在索引里？

正常删除流程会同步更新文档、段落和检索索引，并清理相关缓存。涉及异常中断时，应通过文档列表和问答检索进行复核。

### Q29：清空知识库会删除什么？

清空操作会删除当前知识库中的文档、段落、向量索引以及相关解析/向量/页面/预审核缓存；不会自动删除 `chat_history`、日志或上传目录原始文件。它是高影响操作，正式环境中应增加权限控制、二次确认和备份策略。

### Q30：系统为什么还要保留来源和页码？

因为用户需要能够回到原文核查答案。来源信息可以帮助回答：

- 这句话来自哪份文档？
- 在第几页或哪个章节？
- 是旧版本还是新版本？
- 是否存在其他文档说法不同？

### Q31：系统回答错了，应该先检查什么？

建议按顺序检查：

1. 文档是否确认入库；
2. 解析出的段落和表格是否正确；
3. 问题是否使用了正确的业务范围；
4. 检索来源是否相关；
5. 来源之间是否存在冲突；
6. embedding 模型和检索阈值是否合适；
7. LLM 是否遵守了引用和“不确定时说明”的提示要求。

### Q32：为什么问答答案很短或说“找不到”？

可能原因包括：

- 文档没有确认入库；
- 问题和文档内容差异较大；
- 相似度低于检索阈值；
- 解析内容为空或质量较差；
- 文档内容在图片/复杂表格中，未被正确识别；
- 查询使用了过于口语化或范围不明确的表达。

### Q33：为什么一个问题返回多个来源？

因为多个段落可能共同回答问题，也可能多个文档对同一事项有不同说法。多个来源不一定代表冲突，需要结合来源内容和适用范围判断。

### Q34：系统会自动选择“最新版本”吗？能不能配置？

系统不会根据版本号或发布日期自动推断业务上的最新版本。同一文档族通过 `active`/`inactive` 和 `primary` 保持一个默认生效版本：确认新文档时选择 `new_primary` 会切换主版本，选择 `keep_current` 则保留旧主版本；历史版本仍保留但默认不参与 QA。

当前没有实现 `rag_scope`、按版本号或生效日期排序，也没有问答页面上的多版本检索选择器。文档管理接口支持手工切换某个历史版本为 primary；会话级选择一个或多个版本属于后续设计。

### Q35：可以只做入库，不做矛盾检测吗？

可以根据配置和业务流程调整，但对于制度、合规、运维等场景，不建议完全跳过审核。至少应保留人工确认和来源追溯。

## 15. 当前实现的能力边界

为了避免用户对系统产生不切实际的期待，下面列出当前实现需要注意的边界。

### 15.1 解析质量决定后续质量

如果 PDF 没有正确解析出文字，后面的 embedding、差异检测和问答都无法可靠恢复原文。

```text
解析错误
  → chunk 错误
  → embedding 错误
  → 对比和检索都可能错误
```

所以“先抽查解析结果”非常重要。

### 15.2 相似度不是法律或业务结论

相似度只是数学指标，不等于：

- 两份文档一定属于同一制度；
- 两份文档一定互相矛盾；
- 相似度低就一定没有关系；
- 相似度高就一定应该覆盖旧文档。

### 15.3 版本差异和矛盾不是一个概念

```text
版本差异：同一制度从旧版变成新版，关注“改了什么”
矛盾检测：不同文档对同一事项说法不一致，关注“是否冲突”
```

同一个“每天改成每周”的变化，在版本场景中是版本变更，在独立文档场景中可能是矛盾。

### 15.4 表格支持不是无限的

版本表格比较已经支持表头、列、行和单元格变化，但复杂合并表格、图片表格和无稳定行键的表格仍需人工复核。

### 15.5 LLM 不是最终审批人

LLM 可能受以下因素影响：

- 文本上下文不完整；
- 解析顺序异常；
- 提示词不适合某类业务；
- 模型本身判断不稳定；
- 网络或服务异常。

重要文档仍需要业务人员确认。

### 15.6 当前跨文档表格矛盾检测仍需增强

版本对比中的表格差异比较相对明确；两份独立文档之间的表格冲突，当前覆盖还不完整。这是后续可以独立增强的功能方向。

## 16. 给用户演示时建议使用的讲解顺序

如果向完全不了解技术的用户演示，可以按以下顺序讲：

### 第一步：展示一份空知识库

说明：

> 现在知识库中没有任何文档，因此第一份文档不会产生跨文档矛盾，但系统仍会解析它，并为后续问答建立索引。

### 第二步：上传第一份制度

展示：

- 文件上传成功；
- 解析出了多少段落和表格；
- 预审核完成；
- 确认入库；
- 使用一个明确的问题进行问答。

### 第三步：上传修改后的第二版

准备一个简单变化：

```text
旧版：备份保留 30 天。
新版：备份保留 90 天。
```

展示：

- 系统找到两段相似内容；
- 显示具体文字变化；
- 标记为实质性变化；
- 用户确认后新版入库。

### 第四步：展示不同文档的冲突

准备两份适用范围相近但说法不同的文档：

```text
文档 A：巡检周期为每日。
文档 B：巡检周期为每周。
```

提问：

```text
巡检周期是多少？
```

展示系统返回多个来源或冲突提示，并说明：

> 系统不会替用户擅自决定哪份制度有效，而是把冲突和来源展示出来，交由业务人员判断。

### 第五步：展示表格变化

准备一个表格，把某个周期或责任部门改掉，展示版本对比中的表格行变化。

同时说明：

> 表格版本差异支持结构化比较；复杂图片表格和独立文档表格冲突仍建议人工复核。

## 17. 用户可以如何评价一次审核结果

建议用户不要只看“安全/不安全”一个字段，而要同时看：

1. 文件是否被正确解析；
2. 段落和表格数量是否合理；
3. 比较了哪些已有文档；
4. 文档整体相似度是否合理；
5. 发现了哪些变化；
6. 变化发生在哪一页、哪一章；
7. 是否是版本变化还是跨文档矛盾；
8. LLM 判断是否完整；
9. 是否存在无法比较的文档；
10. 最终是否由业务人员确认。

“没有发现问题”与“系统已经证明没有问题”不是同一个结论。

## 20. 最后总结

用户只需要记住下面六句话：

1. **系统先解析文档，再进行审核，不是直接把 PDF 丢给模型。**
2. **段落和表格会被保留位置，并转换成可比较或可检索的内容单元。**
3. **Embedding 用于找相似内容，文本 diff 和 LLM 用于判断具体变化。**
4. **同一文档的新旧版本重点看“改了什么”，不同文档重点看“是否矛盾”。**
5. **上传完成不等于正式入库，人工确认是防止错误内容进入知识库的最后一道门。**
6. **问答答案应结合来源、页码和适用范围理解，系统是辅助审核工具，不是自动审批人。**

## 21. 六个容易被忽略的工程问题

前文介绍了当前链路，下面把分块、表格、索引规模、噪声配置、小模型评测和版本选择放在一起说明。这里要特别区分：带有“当前实现”字样的是现有代码行为；带有“建议设计”字样的是可以落地、但还需要开发的增强方案。

### 21.1 段落长度到底是多少？能否配置？

当前 PDF 解析使用字符数而不是 token 数衡量段落长度。运行配置中的关键参数是：

```json
{
  "extract": {
    "min_paragraph_length": 10,
    "max_paragraph_length": 600,
    "sentence_break_min_length": 40
  }
}
```

它们的含义分别是：

| 参数 | 当前默认值 | 作用 |
|---|---:|---|
| `min_paragraph_length` | 10 | 普通短文本低于该长度时，通常会被过滤；标题、列表等有结构意义的内容可能例外 |
| `max_paragraph_length` | 600 | PDF 长段落进行二次切分时的普通长度上限 |
| `sentence_break_min_length` | 40 | 文本达到该长度后，遇到句末终止符时才优先作为自然断点 |

“600”不是每个 chunk 都必须精确等于 600 个字符，而是切分算法的控制上限。实际结果可能略短或略长：算法会优先在句号、问号、感叹号等句末位置断开；超过上限时，如果附近存在逗号、分号等软断点，也会优先在那里切开；完全没有自然断点时才强制按长度切分。这里的“字符”也不是 token、字节或页面数量，换用不同语言和 embedding 模型后，600 个字符对应的 token 数会不同。

PDF 跨页段落还有额外约束：当前实现把合并上限设为普通上限的约两倍，因此默认约为 1200 个字符。只有页码连续、前后内容看起来属于同一段、不是新标题或表格，并且合并后不超过上限时，才会尝试合并。Word 路径主要保留 Word 原生段落，不应把 PDF 的 600/1200 规则机械地套到每个 Word 段落上。

这个长度可以配置，但不存在“越大越好”或一个脱离模型的统一无限上限。过小会把完整条款拆碎，降低检索和差异比较的上下文完整性；过大则会导致一个向量混入多个主题，增加提示词长度，并可能超过本地模型上下文窗口。实践上应同时观察：检索命中率、答案引用是否完整、单次提示词 token 数、Embedding 速度和内存占用。建议先在真实文档上比较 300、600、900 等配置，而不是只凭经验修改一个数字。

### 21.2 超长表格会像段落一样自动切分吗？

**当前实现不是这样。** 跨页表格会优先尝试合并，并去除重复表头；确认入库时，`DocStore` 当前把一张表序列化为一个 Markdown Paragraph。因此，一个很长的表格目前可能形成一个很大的检索块，不会自动生成多个带关联 ID 的子表格。表格为空模板的过滤阈值 `table_empty_cell_threshold` 默认是 `0.6`，它只负责过滤低信息量空表，不是超长表格切分参数。

如果表格过长，建议的后续设计是按“表头 + 行组”切分，而不是把 Markdown 任意截断。例如原表为：

```markdown
| 编号 | 检查项目 | 周期 | 责任部门 |
| --- | --- | --- | --- |
| 1 | 数据备份 | 每日 | 运维组 |
| 2 | 日志检查 | 每周 | 运维组 |
| 3 | 权限检查 | 每月 | 安全组 |
```

当一张表需要拆成两个检索块时，子块应重复表头：

```markdown
<!-- table_id=table-017, chunk_index=0 -->
表名：运行检查要求；章节：5.2；表格第 1-2 行
| 编号 | 检查项目 | 周期 | 责任部门 |
| --- | --- | --- | --- |
| 1 | 数据备份 | 每日 | 运维组 |
| 2 | 日志检查 | 每周 | 运维组 |
```

```markdown
<!-- table_id=table-017, chunk_index=1 -->
表名：运行检查要求；章节：5.2；表格第 3 行
| 编号 | 检查项目 | 周期 | 责任部门 |
| --- | --- | --- | --- |
| 3 | 权限检查 | 每月 | 安全组 |
```

重复表头不是冗余错误，而是为了让每个向量块脱离其他块时仍然知道“每日”对应哪一列。每个子块还应保留以下元数据：

```text
table_id          原始逻辑表的稳定 ID
parent_table_id   跨页合并前后的父表 ID；没有父表时可与 table_id 相同
chunk_index       子块序号
row_start/row_end 原表行范围或稳定行键
page_start/page_end 页码范围
chapter           所属章节
document_id       来源文档
```

版本比较时仍应使用父表的 `table_id`、表头、行键和列名进行整表关联；RAG 检索时可以返回某个子块，并通过 `parent_table_id` 继续加载相邻子块或完整表格。若单行本身超过长度上限，不应简单截断单元格，而应保留行键并使用“续行”标记，避免把同一条记录拆成无法解释的两条记录。上述父子表 chunk 方案是建议设计，当前代码尚未实现。

### 21.3 FAISS Flat 什么时候需要升级？百级 PDF 能否单机运行？

不能只按“PDF 文件数量”判断规模。更有意义的指标是总 chunk 数 `N`、向量维度 `d`、查询延迟、并发、索引重建时间和元数据存储量。`IndexFlatIP` 会对查询与索引中的向量进行精确扫描，优点是实现简单、结果可解释；缺点是向量数量增长后，每次查询的计算量近似随 `N` 线性增长。

向量本身的内存可以粗略估算为：

```text
内存 ≈ chunk 数 × 向量维度 × 每个元素字节数
```

例如使用 512 维、`float32` 向量时，仅向量数组大约是：

| chunk 数 | 仅向量数组的理论大小 |
|---:|---:|
| 100,000 | 约 195 MiB |
| 500,000 | 约 0.95 GiB |
| 1,000,000 | 约 1.91 GiB |

实际进程还需要保存文本、页码、文档元数据、FAISS 对象、解析缓存和运行时内存，因此不能按上表直接购买同样大小的机器。若向量维度为 768 或更高，内存还会按比例增加。

对于百级 PDF，若总 chunk 数只有数万到几十万、单机内存足够、并发不高，并且可以接受索引重建和全量扫描的延迟，通常可以先使用单机 FAISS。这里的“可以”是工程经验判断，不是对所有 PDF 的性能保证：一本扫描手册可能比几十份短文档产生更多成本，表格拆分策略也会显著改变 chunk 数。

建议在以下信号出现时进行压测或升级，而不要等待系统完全不可用：

- 总 chunk 数接近约 50 万到 100 万，或内存开始影响解析和模型运行；
- `IndexFlatIP` 查询延迟达不到目标，尤其是在目标并发下；
- 全量重建索引需要几分钟以上，导致新增或删除文档难以及时生效；
- 多个进程或多个服务实例需要共享同一索引；
- 需要按文档、权限、版本、部门或生效状态做稳定的预过滤；
- 需要高可用、备份、水平扩展和在线更新。

这些阈值是启动压测的参考线，不是 FAISS 的硬性限制。可以先通过减少无效 chunk、过滤空表、缓存 Embedding、增加元数据预过滤和采用批量查询延缓升级；之后再评估 HNSW、IVF/PQ 等近似索引或托管向量服务。近似索引通常以少量召回率换取更低延迟或更低存储成本，因此升级后仍需用本项目的真实问题集验证 Recall@k 和答案质量。

### 21.4 在 AWS 中如何扩展？

> 本节是目标方案/后续设计，不是当前部署状态。当前代码没有接入 OpenSearch、DynamoDB、Aurora、Keycloak、S3、Secrets Manager 或托管任务队列；当前仍是本地文件系统、进程内 FAISS 和配置文件。任何云方案都需要单独完成适配、权限、迁移、恢复和区域验收。

如果希望尽量保留当前自定义的 PDF 解析、版本比较、噪声过滤和人工确认流程，比较自然的演进路径是：原文件放在 Amazon S3，解析和审核服务运行在 ECS/EC2 等计算环境，Embedding 和 LLM 可继续使用本地服务或 Amazon Bedrock，向量和可过滤元数据迁移到 **Amazon OpenSearch Serverless 的向量集合**。AWS 文档也提供了由 Bedrock Knowledge Bases 使用或自动创建 OpenSearch Serverless 向量存储的路径，参见 [创建 Amazon OpenSearch Serverless 向量存储](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup-oss.html)。这种方案的优点是可以保留 `document_id`、版本、页码、章节、生效状态等过滤字段，并将当前 Retriever 替换为远程检索实现；缺点是需要自行维护索引写入、字段映射、权限和数据同步。

如果目标是“尽快得到一个标准的托管 RAG”，而不是保留所有当前解析细节，则 **Amazon Bedrock Knowledge Bases** 更省运维。它可以托管从数据源到分块、Embedding、向量存储和检索的一部分标准流程，工作原理可参考 [How Amazon Bedrock knowledge bases work](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)。代价是系统需要适应它的解析、分块、Embedding、同步和检索配置；当前自定义的版本对比、表格父子关联、元数据噪声规则和人工确认流程不能自动原样迁移，通常仍需在 Knowledge Base 之前或之外保留自定义处理层。

因此可以这样选择：

```text
保留当前自定义链路和版本/元数据控制 → OpenSearch Serverless 向量集合
标准 RAG、少写运维代码、接受托管处理流程 → Bedrock Knowledge Bases
百级 PDF、单机仍满足延迟和并发 → 先保留 FAISS，不要为“可能的未来规模”过早引入分布式服务
```

AWS 的向量存储选择还包括其他数据库和托管方式，可参考 [AWS 向量数据库比较指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/choosing-an-aws-vector-database-for-rag-use-cases/vector-db-comparison.html)。最终选择应以压测结果、数据权限、区域可用性、成本和是否必须保留自定义解析为准，而不是只看服务名称。

### 21.5 元数据噪声是正则识别还是 LLM？能否自定义？

两者职责不同，推荐采用“规则优先、LLM 补充、失败保守”的分层方式：

1. **正则和确定性规则**负责日期、版本戳、文件编号、页码跟踪、修订记录表行、空白和常见格式变化。这些规则可解释、速度快，适合在差异进入 LLM 前先归一化。
2. **LLM**只处理规则无法确定的语义问题，例如“运行维护组”与“运维组”是否是同一组织、某行修订说明是否暗示正文发生了变化。LLM 不应负责替代表格结构解析，也不应因为看到“版本”二字就忽略整段内容。
3. **LLM 调用失败或输出不符合约定时**，当前策略应倾向保留差异并标记为需要人工确认，而不是自动归类为噪声。这样会增加少量误报，但能降低漏掉实质变化的风险。

当前版本差异配置已经提供多个可覆盖入口，例如：

```yaml
diff:
  noise_filter:
    enabled: true
    patterns:
      - '修订日期\\s*[：:]\\s*\\S+'
      - '版本号\\s*[：:]\\s*\\S+'
      - '页码\\s*\\d+\\s*→\\s*\\d+'
  cross_noise_filter:
    enabled: true
    patterns: []
    min_length: 6
  tracking_table:
    hints: '修订记录表|有效页清单|发放清单'
    row_patterns:
      - '^\\s*\\d+\\s+.*\\d{4}[-/]\\d{1,2}[-/]\\d{1,2}'
    version_stamp_patterns:
      - 'R\\d+-\\d+'
```

解析阶段还可以通过 `extract.noise_line_patterns`、`extract.noise_patterns` 和相关章节/页眉页脚配置控制哪些内容不进入普通段落。用户追加或覆盖规则时，应先用一组已标注的文档回放测试，检查“漏报实质变化”和“误报元数据”两类结果，不能只看差异数量是否变少。

建议未来提供统一的配置预设，但不要隐藏底层规则：

```text
normal  → 默认忽略常见日期、版本戳和跟踪表噪声，保留业务数值变化
strict  → 只忽略明确匹配的噪声，更多变化进入人工审核
lenient → 允许更多格式和记录变化归入噪声
custom  → 用户在默认规则之上追加、编辑或禁用指定规则
```

其中“最灵敏”不应简单理解为把规则全部关闭后自动得出结论。更准确的做法是关闭或收紧噪声过滤，同时把日期、页码、版本号、空白变化也作为可见差异列出，并将结果标记为 `minor_change` 或“待确认”，这样既不丢失变化，也不会把所有变化误称为业务矛盾。当前代码支持多个分散配置项，但还没有统一的灵敏度 UI 和上述预设管理界面。

### 21.6 7B 以下小模型是否需要开启思考模式？公开评测能说明什么？

**思考模式不是 RAG 的必需条件。** RAG 的基本顺序仍然是“问题向量化 → 检索候选 → 把候选交给模型回答”。模型是否使用额外的 reasoning/thinking token，是生成阶段的策略，不会替代正确的检索、版本过滤和来源约束。

对 7B 以下模型，可以先关闭或限制思考模式用于：

- 简单事实问答、摘要和来源复述；
- 已经有明确单一命中的条款；
- 对延迟、显存和 token 消耗敏感的场景。

对于多个来源冲突、适用范围判断、复杂表格变化等问题，可以有限开启或采用短思考预算，但要验证：延迟是否可接受、模型是否仍然遵守“只依据来源”、是否会输出额外思考内容、JSON 或引用格式是否稳定。思考模式增加 token 消耗并不等于一定提高事实准确率；如果检索候选错误，模型可能只是更长地解释错误依据。

公开资料可以帮助选择评测方法，但不能直接证明某个 7B 以下模型适合本项目：

- [MTEB](https://arxiv.org/abs/2210.07316) 主要覆盖文本 Embedding 的多类任务，可用于比较检索向量模型；它不是本项目端到端问答成绩。
- [BEIR](https://arxiv.org/abs/2104.08663) 是跨领域信息检索评测，可参考 Retriever 的零样本检索能力；公开数据以英文和通用领域为主，与中文制度 PDF 仍有差异。
- [RAGAS 的自动化 RAG 评测论文](https://arxiv.org/html/2309.15217) 讨论了将 RAG 拆成检索和生成质量进行评估的方法，可参考忠实性、答案相关性和上下文相关性等维度。
- [RAGBench](https://arxiv.org/abs/2407.11005) 提供面向多个领域的较大规模 RAG 评测数据和可解释标注，可用于理解端到端 RAG 评测思路，但其模型、数据和任务设置不等于本项目。

对本项目更有价值的是建立一组中文真实问题集，为每个问题标注正确来源、适用版本、关键答案和允许的表述范围，然后分别测量：

```text
检索：Recall@k、Hit@k、MRR、正确版本命中率
生成：答案正确性、来源忠实性、引用准确率、拒答准确率
版本/冲突：实质变化召回率、元数据噪声误报率、冲突判断精确率
工程：首 token 延迟、总延迟、吞吐、显存/内存、JSON 解析失败率
```

因此，公开 Benchmark 适合做模型初筛和指标定义；最终仍应在相同的 Embedding、chunk 规则、版本过滤、提示词、上下文长度和硬件条件下，比较“不开思考”和“有限思考”的本项目测试结果。资料内容为对公开资料的概括，Content was rephrased for compliance with licensing restrictions.

### 21.7 同一文档多个版本能否手工选择一个或几个？

从产品设计上可以，而且比自动猜测“最新版本”更稳妥。建议把选择做成**会话级或问题级检索范围**，而不是删除文档或把其他版本永久设为无效。例如用户在提问前选择：

```text
文档：IT 运维管理规范
版本：R6-2、R6-3、R6-5
检索范围：仅使用已选择版本
```

检索请求可以携带类似下面的范围信息：

```json
{
  "rag_scope": "manual",
  "selected_document_ids": ["doc-r6-2", "doc-r6-5"],
  "selection_mode": "session"
}
```

检索器先按 `selected_document_ids`、版本状态和权限做元数据过滤，再对过滤后的向量集合取 top-k。这样既可以选择一个版本，也可以同时选择多个版本；选择多个版本时，答案应保留每个版本的来源，并在说法不同的时候明确指出差异，而不是把它们拼成一个“平均版本”。

推荐的版本范围设计可以包括：

```text
all_active             → 所有 active 版本
latest_by_added_at     → 按入库时间选择最新
latest_by_version      → 按结构化版本号排序
latest_by_effective_at → 按生效日期选择
manual                 → 用户选择一个或多个版本
```

同时建议在文档元数据中保存 `version`、`effective_date`、`status`、`supersedes_doc_id`、`document_group_id` 和 `priority`。`manual` 选择只改变当前检索范围，不应删除未选中的文档；管理员仍可在后续问题中重新选择它们。

当前代码已经支持通过文档管理接口将某个历史版本切换为文档族的 primary；但这属于全局主版本切换，不等于问答时的会话级版本筛选。当前 RAG 尚未实现 `rag_scope`、页面上的多版本选择器以及按会话传递 `selected_document_ids` 的完整链路。以上按问题选择一个或多个版本的交互属于建议设计，落地时还需要同时处理权限、默认范围、选择过期时间和多版本冲突提示。

## 22. 本节结论

可以把本次补充归纳为六点：

1. 当前普通 PDF 段落默认上限约 600 个字符，最小长度为 10，达到 40 个字符后优先利用句末断点，跨页合并上限约 1200；这些参数可配置，但应以真实问题集和上下文窗口验证。
2. 当前超长表格不会自动拆成带父子关系的多个检索块；后续切分时应重复表头，并保存 `table_id`、`parent_table_id`、`chunk_index`、行范围和页码。
3. 百级 PDF 是否需要升级 FAISS，取决于总 chunk 数和性能指标；数万到几十万 chunk 且并发较低时，单机通常可以先承担，接近 50 万到 100 万 chunk 时应开始压测升级路径。
4. 保留自定义解析和版本控制时，AWS 优先考虑 OpenSearch Serverless 向量集合；标准托管 RAG 则可考虑 Bedrock Knowledge Bases。
5. 元数据噪声适合由正则/规则先处理，LLM 负责不确定的语义判断，用户应能够追加、覆盖或禁用规则；LLM 失败时保守保留差异。
6. 7B 以下模型不必默认开启思考模式；公开评测可用于模型和方法初筛，但必须用中文真实文档、固定检索链路和版本标注集做最终验证。手工选择一个或多个版本应作为检索范围过滤，而不是删除未选版本。

## 23. 对 Embedding 长度、性能和 AWS 区域的进一步说明

### 23.1 “512 长度”到底指什么？

当前默认模型 `BAAI/bge-small-zh-v1.5` 中有两个容易混淆的 512：

- **Embedding 维度是 512**：每段文本最后被表示为 512 个浮点数。这决定向量占用多少内存，以及 FAISS 每次计算的维度；它不是输入字符串最多只能有 512 个字符。
- **模型位置上限是 512 个 token**：模型配置中的 `max_position_embeddings` 为 512，输入过长时会受到 tokenizer/推理后端的最大长度限制。token 不是字符，在中文、英文、数字、标点和 Markdown 混合时，字符数与 token 数并不固定。

因此，“512 维”不能直接换算成“512 字符”。当前解析器的 600 字符上限是版面切分参数，并不等于 Embedding 模型的安全输入长度。尤其是中文长句、英文路径、数字、表格 Markdown 表头和分隔符混在一起时，600 个字符可能接近或超过模型输入上限；如果后端截断，尾部信息可能没有参与向量计算。

对当前中文制度文档，一个可以先行压测的范围是：

```text
普通条款：约 200～400 个中文字符
较完整段落：约 300～500 个字符，但必须检查实际 token 数
表格子块：表头 + 适量行组，优先保证每个子块低于模型 token 上限
```

这不是模型保证的“最佳答案”，而是工程起点。更可靠的方法是用实际 tokenizer 统计一批真实段落的 token 长度，观察 95/99 分位数，再决定 `max_paragraph_length`。如果真实文档中长中文段落很多，可以把 600 下调到 400～500，并通过召回率、答案引用完整度和截断比例验证；如果段落很短，则不必为了追求某个固定数字强行拼接。

当前文章中“约 1200 字符”的跨页合并上限应理解为解析器的合并控制值，而不是建议把 1200 字符原样交给当前 BGE 模型。跨页合并后仍应在 Embedding 前做 token 长度检查，必要时再次按语义边界切分；这项二次 token-aware 切分目前尚未在当前代码中独立实现。

### 23.2 父子表格设计是否合理？应该如何改进？

“父表 + 子表块”的方向是合理的，但仅使用 `parent_table_id` 还不够。因为同一逻辑表在不同文档版本中，既需要知道它们可能对应同一张业务表，也必须区分每个版本的实际表和每个表的检索子块。建议采用三层标识：

```text
logical_table_id   跨版本尝试关联的逻辑表 ID
 table_instance_id 某一份文档/版本中解析出的完整表实例 ID
 table_chunk_id    该表实例拆出的具体检索子块 ID
```

也可以把 `parent_table_id` 保留为 `table_instance_id` 的别名，但不要让不同版本的完整表错误地共用同一个父 ID。一个更完整的元数据例子是：

```json
{
  "logical_table_id": "manual-5-2-check-items",
  "table_instance_id": "doc-r6-5-table-017",
  "table_chunk_id": "doc-r6-5-table-017-chunk-001",
  "chunk_index": 0,
  "row_start": 1,
  "row_end": 20,
  "page_start": 18,
  "page_end": 19,
  "chapter": "5.2 数据备份要求",
  "document_id": "doc-r6-5"
}
```

这样设计的好处是：RAG 可以命中 `table_chunk_id` 后按 `table_instance_id` 加载相邻行；版本对比可以使用 `logical_table_id` 作为候选关联线索，再通过表头、列名和行键确认；用户打开来源时仍然能回到具体文档版本和页码。若表格只是一次性出现，没有跨版本关联依据，`logical_table_id` 可以为空或只在文档内生成。

子块重复表头仍然是合理的，因为向量检索返回的是独立文本块；但应避免只重复表头而丢掉表名、章节和适用范围。对跨行合并单元格、没有稳定行键或一行特别长的表格，建议增加“续行”标记和原始行编号，不要把一个业务记录无提示地拆成两个互不相干的向量。上述三层 ID 和按表实例加载相邻块是建议设计，当前项目仍未实现自动表格子块切分。

### 23.3 FAISS 的规模和耗时不仅由内存决定

内存只是能否运行的第一道条件，耗时同样重要。对于当前归一化向量 + `IndexFlatIP`，可用粗略模型表示：

```text
向量存储空间：O(N × d)
单次查询计算量：O(Q × N × d)
批量/重建计算量：随 N、d 和批量大小近似线性增长
```

其中 `N` 是 chunk 数，`d` 是向量维度，`Q` 是一次查询中的向量数量。实际耗时还受 CPU 指令集、线程数、内存带宽、批量大小、并发、文本元数据处理和索引读写方式影响。因此，100 万个短文本向量不一定和 100 万个带复杂元数据的块表现相同，但 Flat 索引的核心扫描量仍会随 `N` 增长。

CPU/GPU 的影响要分开看：

1. **Embedding 计算**：当前配置的 `device=auto` 可以让 fastembed/ONNX 在可用环境中使用 GPU；没有 GPU 时回退 CPU。长文档首次入库时，这一阶段通常可能是主要耗时。
2. **FAISS 检索**：当前代码构造的是 `IndexFlatIP`。Windows 环境安装的是 `faiss-cpu`，所以即使 Embedding 在 GPU 上，FAISS 搜索并不会自动变成 GPU 搜索；Linux 中安装 GPU 版本并显式把索引迁移到 GPU，才可能使用 GPU 检索。
3. **数据传输和并发**：小索引放到 GPU 后，CPU/GPU 数据传输开销可能抵消收益；多个并发请求还会争用显存和计算资源。不能看到“有 GPU”就直接假设整体问答会按比例加速。

因此升级判断应至少同时记录：P50/P95 查询延迟、Embedding 延迟、索引重建时间、并发下的吞吐、峰值内存/显存、召回率和文档新增后的生效时间。先用真实 chunk 和真实问题做基准测试，再决定是否继续 Flat、改用 GPU Flat、采用 HNSW/IVF/PQ 或迁移向量服务。

### 23.4 AWS 方案要区分全球区域和中国区

此前“推荐 Bedrock Knowledge Bases”的说法需要加上区域前提。Amazon Bedrock Knowledge Bases 是全球 AWS 区域中的托管 RAG 选项，但不能因为当前配置使用了 Bedrock API，就假设它在 AWS 中国区同样可用。AWS 服务和模型都按区域提供，部署前必须核对官方区域与模型清单；截至本文本次核对，没有把北京或宁夏区域作为 Amazon Bedrock Knowledge Bases 的常规部署区域来规划。中国区项目不应直接复用 `us-east-1` 配置，而应先确认账号、区域、模型、跨境传输和合规要求。

#### 小规模：先保留单机 FAISS

适合文档量较小、并发低、允许单实例维护的情况：

```text
S3：保存原始 PDF、备份和审核产物
EC2：运行当前解析、版本比较、RAG 服务和 FAISS
EBS：保存本地索引、解析缓存和运行日志
```

中国区可在北京或宁夏区域选择合适的 EC2/EBS/S3 组合；Embedding 使用本地模型，LLM 使用经过评估的本地模型或在合规前提下接入可用的外部模型服务。优点是改动小、固定成本容易估算、无需维护分布式向量服务；缺点是单机故障、扩容和多实例共享索引需要自行处理。百级 PDF 如果仍在数万到几十万 chunk 且实测延迟可接受，优先采用这个方案通常比提前上 Serverless 更经济。

#### 中等规模：自定义解析 + 托管向量检索

当需要多实例、高可用、元数据过滤、在线更新或更高并发时，可以保留当前解析、版本比较和人工确认服务，把确认后的向量与元数据写入：

- **Amazon OpenSearch Serverless 向量集合**：AWS 中国区官方文档提供了向量搜索集合说明，支持相似度搜索、过滤字段和按工作负载扩展，参见 [中国区 OpenSearch Serverless 向量搜索](https://docs.amazonaws.cn/en_us/opensearch-service/latest/developerguide/serverless-vector-search.html)。其容量按 OCU 管理，参见 [中国区 OpenSearch Serverless 容量管理](https://docs.amazonaws.cn/en_us/opensearch-service/latest/developerguide/serverless-scaling.html)。优点是少维护节点、便于多实例共享和元数据过滤；缺点是 OCU、索引和请求费用需要监控，最低容量、冷启动和最大容量设置会影响成本与延迟。
- **Amazon Aurora/RDS for PostgreSQL + pgvector**：如果 chunk 数中等、系统已经需要关系型元数据、版本状态和事务能力，可以把向量和文档元数据放到 PostgreSQL。优点是查询、权限和业务表容易统一；缺点是需要自行设计索引、扩容、备份和向量检索调优。中国区可以参考 [中国区 Aurora PostgreSQL 作为向量知识库的文档](https://docs.amazonaws.cn/en_us/AmazonRDS/latest/AuroraUserGuide/AuroraPostgreSQL.VectorDB.html)，但具体可用版本和扩展仍需在目标区域核对。

中等规模的常见组合是：S3 + ECS/EC2 上的解析审核服务 + OpenSearch Serverless 或 Aurora/RDS + 本地/区域可用的 LLM。不要把 Bedrock Knowledge Bases 强行放在中国区架构中；如果 LLM 也不能出境，就需要把生成模型部署在中国区可用的计算资源上，或者使用经过合规评估的区域内模型服务。

#### 中国区之外的标准托管方案

如果数据和部署区域允许使用 Amazon Bedrock，标准方案可以是：

```text
S3 数据源
  → Bedrock Knowledge Bases
  → 托管分块与 Embedding
  → OpenSearch Serverless / 其他受支持向量存储
  → Retrieve 或 RetrieveAndGenerate
```

但这不是当前代码的“低成本开关”。当前项目自己负责 PDF 解析、表格结构、版本比较、FAISS 检索和来源映射；接入 Knowledge Bases 后，需要新增数据同步、Knowledge Base/数据源管理、检索 API 适配、过滤条件、引用格式转换和错误重试。若直接把原 PDF 放入 S3 让 Knowledge Bases 重新解析和分块，当前自定义的 600 字符规则、父子表格 ID、版本噪声处理和审核边界都不会自动原样保留。

因此，当前代码接入 Bedrock Knowledge Bases 的改动量属于**中到大**，不是修改一个 `provider` 就完成：

```text
LLM 继续调用 Bedrock Converse              → 小改动，只替换/调整生成模型配置
使用 Bedrock Knowledge Bases 做检索         → 中到大改动，需要新增 KB 检索适配层
让 Knowledge Bases 接管解析、分块和入库      → 大改动，需重新设计当前自定义文档链路
```

如果部署在 AWS 全球区域且更重视减少运维，可以把 Knowledge Bases 作为新的标准 RAG 后端，与当前自定义版本比较链路并行；如果部署在 AWS 中国区或必须保留当前解析和版本控制，应优先选择“单机 FAISS → OpenSearch Serverless/Aurora pgvector”的渐进路线。成本判断也应包含固定容量、请求量、索引写入、模型调用、跨区流量、备份和运维人力，而不能只比较某个向量服务的单价。

## 24. 章节元数据、分段重叠和 difflib

### 24.1 章节标题会不会一起参与 Embedding？

当前实现中，章节标题、章节编号、页码和来源文件会保存在 `Paragraph` 的结构字段中：

```text
Paragraph
├── text           正文文本
├── chapter        章节编号
├── chapter_title  章节标题
├── page/page_end  页码范围
├── source_file    来源文件
└── location       面向用户的定位信息
```

**当前 RAG Embedding 实际使用的是 `Paragraph.text`，不是完整的 `Paragraph.to_markdown()`。** 也就是说，普通段落的章节编号和章节标题当前主要作为附属元数据，用于来源定位和展示；它们不会自动以文本前缀拼接到向量输入中。表格在入库时会先转换为 Markdown 文本，但当前表格向量输入也主要是表格 Markdown 本身，章节标题保存在表格对象和生成 Paragraph 的字段中。

因此当前链路更接近：

```text
正文 text                         → 计算 Embedding
章节编号/标题/页码/来源            → 保存为元数据，用于定位、展示和后续过滤
```

这和“章节标题完全没有价值”不是一回事。章节标题仍然会影响解析时的段落归属，问答返回来源时会出现在 `location` 中；只是它当前没有直接参与向量相似度计算。

一个可以考虑的后续设计是构造单独的向量输入文本：

```text
章节：5.2 数据备份要求
正文：系统管理员应每日执行一次数据备份……
```

同时继续把原始正文和章节字段分别保存。这样“备份要求”之类的章节主题有机会帮助检索，但也可能让重复出现的通用标题放大噪声，因此不能未经评测就把所有标题盲目拼接。建议通过 A/B 测试比较“正文向量”和“章节标题 + 正文向量”的 Recall@k、误命中率和上下文长度。当前代码尚未启用这种标题前缀 Embedding 方案。

### 24.2 长段落二次切分时有没有重叠？

**当前默认没有滑动窗口重叠。** `split_stream()` 在自然断点或长度上限处结束当前段落，然后从下一个字符/行继续建立新段落；它不会自动把上一段末尾的几十个字符复制到下一段。跨页合并也属于段落恢复，不是 chunk overlap。

当前行为可以简化为：

```text
原文：A B C D E F G
切分：Chunk 1 = A B C
      Chunk 2 = D E F
```

而带重叠的切分会是：

```text
Chunk 1 = A B C D
Chunk 2 = D E F G
```

不重叠的优点是向量数量更少、内存和检索结果去重压力较低，也不会重复计入同一条款；缺点是如果关键条件正好位于切分边界，单个 chunk 可能缺少前后语境。后续可以增加可配置的 `chunk_overlap`，但应优先按句子、条款或列表项重叠，而不是简单复制固定字符数。例如可以复制上一块最后 1～2 句，或在二次长度切分时保留 30～80 个字符的语义尾部。

重叠也不是越大越好：它会增加 Embedding 计算、索引大小和重复命中；同一事实被多个 chunk 返回时，还可能挤占 top-k 中其他有价值内容。建议把 `chunk_overlap` 设为 0、少量句子和固定字符数几个候选，在真实问题集上比较边界问题的 Recall@k 与索引膨胀比例。当前代码没有统一的 `chunk_overlap` 配置，文章中“跨页合并”不能理解成“已经实现了 chunk overlap”。

### 24.3 difflib 是什么？和 LLM 有什么区别？

`difflib` 是 Python 标准库中的文本序列比较工具。项目主要使用其中的 `SequenceMatcher`，把文本看作字符或字符串序列，寻找相同片段和不同片段，并输出 `equal`、`insert`、`delete`、`replace` 等操作。它不需要调用网络或模型，结果确定、速度快、容易复现。

例如：

```text
旧版：系统管理员每天执行一次备份。
新版：系统管理员每周执行一次备份。
```

`difflib` 擅长回答：

```text
哪些字符或片段被删除了？
哪些字符或片段被新增了？
哪一段被替换了？
两段文本的表面序列相似度是多少？
```

当前项目中，`difflib` 用于多个确定性环节，包括：

- 文本差异片段定位和高亮；
- 将删除段落与新增段落进行二次相似匹配，识别可能的改写或移动；
- 表格表头、列名和行文本的相似度计算；
- 在明显的纯新增、纯删除差异中生成确定性摘要；
- 在进入 LLM 前做部分文本预分类。

它的优势是：

| 方面 | difflib |
|---|---|
| 运行方式 | 本地确定性计算，不依赖网络或模型服务 |
| 擅长内容 | 字符/词序列的新增、删除、替换和相似片段定位 |
| 结果特点 | 可复现、可解释，适合高亮和逐字核对 |
| 成本 | 通常低，适合批量处理小段文本 |
| 局限 | 不理解业务语义、同义词、适用范围和真正矛盾 |

`difflib` 不擅长以下判断：

```text
“每日”改成“每周”是否违反制度要求？
“运维组”与“运行维护组”是不是同一个组织？
两份数字不同的规定是否因为适用范围不同而不冲突？
一段内容虽然换了大量说法，是否仍然表达同一要求？
```

LLM 的职责不同。LLM 可以结合上下文、适用范围和提示词，对差异做语义归类、摘要和冲突判断，但它可能受模型能力、提示词、上下文长度、服务异常和输出格式影响，结果不一定稳定，也不适合替代精确字符定位。

Embedding 也不是 difflib 或 LLM 的替代品：

```text
Embedding → 找可能对应的段落
 difflib  → 找具体文字和序列变化
规则      → 识别日期、编号、数值等确定性模式
LLM       → 判断不确定的语义含义、范围和冲突
人工审核  → 对重要业务结论做最终确认
```

当前版本对比的推荐流程就是分层处理：先精确文本配对和结构化表格比较，再用 Embedding 找语义候选，使用 `difflib` 定位文字变化，规则优先识别明确的数值或元数据变化，最后只把规则无法确定的部分交给 LLM。这样既不会让 LLM 负责它不擅长的逐字 diff，也不会把字符相似度误当成业务结论。

### 24.4 刷新浏览器后，未完成上传为什么会消失？

当前系统需要区分三个时刻：

```text
浏览器上传文件
  ↓
服务端完整读取并保存文件
  ↓
创建 task_id 和预审核任务
  ↓
后台开始预审核并通过 SSE 推送进度
```

如果刷新发生在第二步之前，浏览器会中断当前上传请求，服务端可能还没有创建 `task_id`；刷新后自然找不到待审核任务。如果 `task_id` 已经创建，且服务没有重启，刷新页面通常会调用 `/review/active`，重新找到 `pending/running` 任务并连接 SSE。

但当前任务持久化有明确限制：磁盘上的 `review_tasks.json` 只保存已经有结果的 `done/confirmed/rejected` 任务，不保存 `pending/running/paused` 的后台任务和进度字段。服务重启时，进程内任务字典和 `asyncio` 后台任务都会丢失。因此，**如果第 5 个文档当时已经创建任务但随后后端重启，它从页面消失是预期结果；如果只是普通浏览器刷新且任务已经进入运行态，则更可能是刷新发生在 task_id 创建之前、任务处于 paused，或 `/review/active` 请求失败。**

还有一个当前前端边界：后端会返回 `paused` 任务，但页面初始化恢复分支尚未为 paused 任务显示进度区和重连 SSE。后续应补充 paused 恢复，并考虑为未完成任务设计持久化检查点或重启后自动标记为“可重跑”，避免上传文件变成没有任务记录的孤儿文件。
