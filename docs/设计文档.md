# 设计文档（Design）

> simple_rag 关键设计决策与实现原理 ｜ 代码状态：2026-08 全量重构 + 08-12 ~ 08-15 迭代优化

本文记录系统在重构过程中沉淀的核心设计决策，解释"为什么这样做"，供后续维护与扩展参考。

---

## 1. 模块拆分与依赖治理

**决策**：业务按"解析 / LLM / 差异 / 应用"四象限拆分为 4 个包，依赖严格单向、禁止循环。

**理由**：
- `doc_parser` 与 `llm_chat` 是通用能力，不应反向依赖业务。
- `version_diff` 是被复用最多的"算法核心"，独立于 Web 框架，便于单测与脚本化调用（如 `examples/verify_version_diff.py`）。
- `rag_server` 是唯一编排层，把三者组装成产品。

**落地**：依赖通过正式的包导入表达（`from doc_parser import parse`、`from llm_chat import ask_once`、`from version_diff import DiffEngine`），生产代码无 `sys.path` 注入。项目采用 **uv workspace**——根 `pyproject.toml` 声明 `members`（4 模块），各模块 `[tool.uv.sources]` 以 `{ workspace = true }` 引用兄弟包，根级 `uv.lock` 统一锁版本，`uv sync --project rag_server` 后即按正式包名导入，无需路径 hack。

---

## 2. 文档解析模型（doc_parser）

**决策**：解析结果统一为 `Document(paragraphs, tables)`，段落/表格为带定位信息的 dataclass，并提供 `to_dict()/from_dict()`。

**关键点**：
- `Paragraph` 字段：`text, page, page_end, chapter, chapter_title, source_file, index`；`location` 为只读属性（"第3-4页 / §2.2 / 备份策略"）。
- `Table` 字段：`rows, headers, page, page_end, chapter, chapter_title, context_before, source_file, index`。
- **跨页表格合并**：`_merge_cross_page_tables` 通过表头相似度判断相邻表格是否同一张，自动合并。
- **表格章节归属**：`_assign_table_chapters` 把表格绑定到页面号≤其页码且最近的带章节段落。
- **单一序列化来源**：缓存（`parse_cache`）与落盘（`doc_store`）一律通过 `to_dict/from_dict`，消除此前"各处手抄 dict 字面量"的漂移风险。

---

## 3. 语义配对 + 字级 diff（version_diff）

**决策**：版本对比不依赖机械的"第 N 段 vs 第 N 段"，而是先做**语义向量配对**，再对配对成功的段落做**字符级 diff**。

**流程（`version_compare`）**：
1. 解析新旧两版 → embedding（按文件级缓存）。
2. `matcher.pair_paragraphs`：用 FAISS / 向量相似度把"语义对应"的段落配对，相似度 ≥ `similarity_threshold`（默认 0.80）才配对。
3. 配对成功且文本不同 → `modified`（记录 `old_text/new_text/similarity`）。
4. 旧版独有 → `removed`；新版独有 → `added`。
5. 表格：按表头文本相似度配对（`_compare_tables` → `_compare_table_pair`，逐行 `_row_key` 比较），未配对的整表标记为 added/removed。
6. LLM 过滤（`_filter_substantive_changes`）：剔除纯标点/空白/格式刷差异，仅保留语义变更。

**理由**：企业文档修订常伴随增删与重排，行号对齐会大量误报；语义配对更贴近"人类觉得这两段在讲同一件事"的直觉。

## 4. 规则预过滤表（prefilter）

**决策**：`pre_classify`（决定某处差异是否值得送 LLM 判定）由 8 条 `if` 链重构为 **`_PRECLASSIFY_RULES` 规则表**（9 个谓词函数）。

**理由**：线性 `if` 链难以增删规则、难以测试；规则表使"新增一种噪声类型"变为"加一个函数 + 一行注册"，且每条规则可独立单测。行为与原实现保持等价。

---

## 5. LLM 判定协议（judge_pairs）

**决策**：对外暴露鸭子类型的 `judge_pairs(pairs, llm_config, judge_config)` 公共接口，调用方只传 `{"a": {text, source_file, location}, "b": {...}}` 字典，无需感知内部 `TextDiffItem`。

**报文约定**：
- 输入：`pairs` 为段落对列表。
- 输出：`list[dict]`，每项 `{"index": 1-based, "inconsistent": bool, "point": str, "doc_a_says": str, "doc_b_says": str}`；LLM 不可用时返回 `None`。
- 提示词：内置 `prompts/consistency_judge.txt`，支持通过 `judge_config.prompt_file` / `prompt_template` 覆盖（`.format()` 占位符 `{count}`/`{items}`，JSON 示例用 `{{`/`}}` 转义）。

**理由**：让 RAG 问答的冲突判定与预审核的矛盾判定**复用同一底层**，避免两套 prompt 与两套解析逻辑分叉。

---

## 6. 统一冲突检测（conflict.py）

**决策**：将原本分散在 `engine.check_conflicts`（自建 `Paragraph`/`TextDiffItem` 调 `filter_diffs`）与 `qa_engine._detect_conflicts`（三 private 方法）的两套实现，收敛为**单一公共入口 `detect_conflicts()`**。

**统一算法**：
```
passages ─► 跨文档 + 非相同文本预过滤
          ─► 带 score 时叠加 score/相似度门控（Jaccard 2-gram）
          ─► _llm_confirm（复用 judge_pairs）
          ─► LLM 成功 → 返回确认结果
          └─ LLM 不可用 → _heuristic_group（按 doc_a 分组聚合）
```

**统一结果结构**：
```json
{
  "point": "...",
  "doc_a_file": "...", "doc_a_location": "...", "doc_a_says": "...",
  "doc_others": [{"file": "...", "location": "...", "says": "..."}]
}
```

**收益**：
- `engine.check_conflicts` 与 `qa_engine._detect_conflicts` 都委托同一实现，输出形状逐字段不变（前端 `build_conflict_context` 零改动）。`qa_engine._detect_conflicts` 方法名虽保留，但现为**薄委托**（把 `RetrievedChunk` 转成 `passages` dict 后调用 `detect_conflicts`），不再含自写逻辑。
- 消除了 `qa_engine` 中"绕开 matcher 自写 `_text_similarity`"的坏味道。
- 顺带修复了原 LLM 确认路径下 `doc_others` 缺 `file` 键的潜在 KeyError。

---

## 7. LLM + JSON 抽取工具（llm_util.call_llm_json）

**决策**：把 judge 与 engine 中重复的"调用 LLM + 正则抽取 JSON 数组"逻辑抽为 `call_llm_json(prompt, llm_config, max_retries=2, retry_backoff=1.0)`。

**健壮性设计**：
- **两类失败重试**（指数退避，含首次最多 `max_retries+1` 次）：① `ask_once` 抛异常（瞬时网络/超时）；② 返回了内容但 `json.loads` 解析失败（模型偶发把 JSON 裹在 markdown）。
- 空响应直接返回 `None` 不重试。
- 单批 JSON 瑕疵被优雅降级（跳过该批、记 warning），不阻断整体差异识别。
- 签名向后兼容（新增参数为可选），judge / engine 调用方零改动即受益。

---

## 8. 配置分层（rag_server）

**决策**：运行配置分两层——**默认配置（`config_store.DEFAULT_CONFIG`）+ 文件覆盖（`config.json`）**，且 LLM 采用 **profiles + routing** 模式。

**结构**：
```jsonc
{
  "llm_profiles": {
    "self_hosted_glm": {...}, "bedrock_glm_flash": {...}, "deepseek": {...}
  },
  "llm_routing": { "qa": "bedrock_glm_flash",
                   "pre_review": "bedrock_glm_flash",
                   "conflict_detection": "bedrock_glm_flash" },
  "embedding": {...}, "retrieval": {...}, "pre_review": {...},
  "judge": {...}, "conflict_detection": {...}, "prompts": {...}, "chat": {...}
}
```

**关键约定**：
- `config.json` **不入库**（`.gitignore` 排除），新环境复制 `config.example.json` 后修改。
- `ConfigStore.get_llm_profile(use_case)` 按 routing 取对应 profile；profile 缺失时 fallback 到第一个。
- 环境变量覆盖（分两条路径，注意适用范围不同）：
  - **LLM 相关**（`LLM_BACKEND`、`LLM_MODEL`、`LLM_BASE_URL`、`AWS_REGION`）：在 `llm_chat/defaults.py` 生效，影响 `llm_chat` 的默认后端/模型名/区域/base_url。
  - **Embedding 相关**（自 08-14 起基于 fastembed / ONNX，零 torch 依赖；`device_utils.embedding_model_kwargs` 返回的 `torch_dtype` 在有 torch 时为真实 `torch.dtype` 枚举、无 torch 时回退为 `"torch.float16"` 字符串）：
    - `EMBEDDING_MODEL`、`SIMPLE_RAG_EMBEDDING_DTYPE`：仅作为 `version_diff/config.py::Config.embedding` 的**无参默认值**来源；当调用方显式传入 `embedding` 配置段（如 rag_server 的 `_build_engine_config` 从 `ConfigStore` 传入）时**不生效**。
    - `SIMPLE_RAG_EMBEDDING_DEVICE`：在 `version_diff/device_utils.py::resolve_embedding_device` 生效，优先级**高于** `config.json` 的 `embedding.device`（rag_server 路径也适用）。
  - 注意：**rag_server 应用的 embedding 模型名/dtype 仅从 `ConfigStore`（`config.json`）读取**，不受上述环境变量影响；只有 `SIMPLE_RAG_EMBEDDING_DEVICE` 在应用路径下生效。

---

## 9. 预审核编排（review_runner）

**决策**：把原先冗长的 `run_pre_review` 拆为 3 个模块级 helper：
- `_compute_doc_signature()`：文档名签名，用于缓存失效。
- `_build_engine_config()`：组装 `DiffEngine` 配置。
- `_run_version_compare()`：版本对比封装（try/except，失败返回 `[]`）。

**理由**：原函数是"上帝函数"，难以测试与改动；拆分后每个 helper 可独立单测，失败隔离更清晰。

---

## 10. 持久化与缓存策略

| 缓存 | 用途 | Key | 失效 |
|------|------|-----|------|
| parse_cache | 解析结果 | 文件 SHA256 | 上传内容变化即失效 |
| vector_cache | Embedding 向量 | 段落内容哈希 + 段落数 + 配置哈希 | 内容/解析配置/embedding 模型任一变化即失效 |
| page_cache | PDF 页面 PNG | 文件+页码 | 手动清空 |
| review_cache | 旧版文档路径缓存 | 任务 | rerun 时删除 |

- 上传文件按 `SHA256 + 原扩展名` 命名，避免同名覆盖；写入用临时文件 + `os.replace` 原子提交。
- 解析结果用 `to_dict/from_dict` 序列化，是落盘唯一格式。

## 12. 迭代记录（2026-08-12 ~ 08-15）

> 记录全量重构之后的小步迭代，便于维护者了解"为什么这样改"，避免文档与代码再次漂移。

### 12.1 llm_chat — 异常状态传递与后端去重（08-12）
- `backends/base.py` 的 `_send()` 抛 `RuntimeError` 时挂 `status_code` / `is_network_error` 属性；`retry.py` 改用 `getattr` 读取属性决定重试，**删除**原先从异常文本正则抠状态码的 `_STATUS_RE` / `_extract_status_code`。消除 base↔retry 之间的隐式字符串格式耦合（改错错误信息文案曾会让重试静默失效）。
- `BaseHTTPBackend` 新增 `_init_common()` 集中处理 6 个公共字段（api_key_env / api_key / max_tokens / timeout / max_retries / retry_backoff）；`bedrock.py` / `openai.py` 仅保留各自特有字段，消除样板重复。

### 12.2 跨模块重复消除（08-12）
- `version_diff/llm_util.call_llm_json` 原先手写 10 行 `.get()` 透传，改为调用新增的 `llm_chat.ask_once_with_config(prompt, llm_config, system_prompt)`（provider→后端，其余透传）。`ask_once_with_config` 内部委托 `ask_once`，外部测试零改动。
- `rag_server` 中 PDF 页数计算原本 3 处实现、2 个库（fitz / pdfplumber），统一为 `app/services/utils.get_pdf_page_count()`（fitz，失败返回 0）。

### 12.3 ChatSession.ask 错误处理契约修正（08-13）
- **问题**：`session.ask` 对 `RuntimeError` 向上抛，但对其他 `Exception` 返回 `"[错误] LLM 调用失败: ..."` 字符串。由于没有任何调用方检查该前缀，失败的 LLM 调用会被当成**正常答案**以 HTTP 200 返回给用户。
- **修正**：`ask` 统一向上抛出；`rag_server/app/routes/qa.py` 将 LLM 层错误（`RuntimeError`，含 API Key 缺失 / 网络超时 / 重试耗尽）映射为 **503**，其余异常为 500。符合 `test_web_api` 既定契约（200 成功 / 503 降级，非 500 内部崩溃）。
- 配套：原 `test_session.py::test_backend_error_handling` 断言返回 `[错误]` 字符串，改为断言异常向上抛出（`pytest.raises`）。

### 12.4 依赖管理重构 + Embedding 改造（08-14）
- **uv workspace**：四个独立模块（各带独立 `uv.lock`、可编辑本地路径 `editable = true`）改为单个 **uv workspace**——根 `pyproject.toml` 声明 `members`，模块间用 `[tool.uv.sources] { workspace = true }` 引用，移除各模块 `uv.lock`，统一收敛为根 `uv.lock`。收益：一次 `uv sync --all-extras` 装齐 4 模块 + extras，避免四份 lock 漂移；新增根级一键脚本 `scripts/install_system.py`（替代模块内 `install_deps.py`），统一处理 GPU 检测→torch 构建→全量 sync。
- **Embedding：sentence-transformers → fastembed**：`version_diff/device_utils.py` 新增 `EmbeddingModel` 适配器（`load_embedding_model`），底层 `fastembed.TextEmbedding`（ONNX Runtime），输出与 `SentenceTransformer(normalize_embeddings=True)` 等价（L2 归一化 float32）。下游 `VectorStore` / `DocStore` / `DiffEngine` 只依赖 `.encode()` 签名，无需感知后端。收益：核心检索链路**零 torch 依赖**，安装体积与内存占用更低；`device_utils.embedding_model_kwargs` 的 `torch_dtype` 保持"有 torch 回真实枚举 / 无 torch 回字符串"双路行为。

### 12.5 torch 策略 + mineru extra 收敛（08-15）
- **torch 策略**：从"无 GPU 跳过 torch"改为"**无 GPU 也装 CPU 版 torch**"（有 GPU 装 CUDA 版，默认 cu124）。理由：docling / mineru 解析后端均需要 torch；CPU torch 下 mineru 用 `pipeline` 模式可运行（慢但可用），使**深度学习解析能力与 GPU 有无解耦**。
- **mineru extra 收敛**：`mineru[all]` → `mineru[pipeline,vlm]`。只装 pipeline（OCR/布局）与 vlm 两档引擎，**不再安装 lmdeploy / vllm** 重型推理框架，Windows/Linux 均可安装。
- **实测**：CPU torch（2.8.0+cpu）环境成功端到端解析 9 页真实 PDF（mineru pipeline，86s，33 段 + 1 表）；embedding（fastembed）与三个后端（pdfplumber / docling / mineru）均可加载。

### 12.6 PDF 解析后端选型与默认切换（08-16）
- **新增 PyMuPDF 快路径后端**（`bk_pymupdf`）：数字文本 PDF 秒级解析（116 页手册 4.99s vs pdfplumber 9.75s）；`select_backend` auto 路由升级（扫描件→mineru、无框线表格→docling、数字文本→pymupdf）。
- **默认解析后端切 pdfplumber**：基于 R3-2→R3-3 的 LLM 研判——docling 布局模型偶把标题行插入段落造成碎句（§3.2.6 段落被拆成 3 个碎片），pdfplumber 段落完整且找到真实修改（§6.1.4 科室→处室）。默认 `pre_review.parse_backend=pdfplumber`（docling 保留给无框线表格场景）。
- **GPU 全链路**：`faiss-cpu→faiss-gpu`、`onnxruntime-gpu`（embedding CUDA provider，需并行=None 避免 fastembed pool 崩溃/泄漏）、docling `batch_size` 可配（T4 上 16-32 快约 16%）。

### 12.7 解析质量与版本对比准确度（08-16）
- **解析缓存**（`version_diff.parse_cache`）：version_compare/预审核/入库统一按"文件 SHA256+解析配置签名"缓存，重复解析秒级；`_serialize` 去掉 300 字符截断。
- **docling 后处理**：碎尾合并（布局模型拆散的相邻 TextItem 拼接）、页眉前缀剥离（每页手册名从段首剥离，168→0 段）。
- **版本对比**：`pair_paragraphs` 精确文本优先配对（消除重复短文本抢占，假差异 106→13）；removed/added 二次配对（改写/移动合并为 modified，如"OKAIR 无线连接→VPN 连接"）；removed×modified 吸收（旧版半句被新版并入改写段落开头时，子串命中即剔除 removed，如"用户应自行承担访问互联网内容的责任"被并入 §5.1.7 补全段）；表格行（`location` 以"行:"/"表格"开头）不参与二次配对与吸收（整行替换是真实变更，如 VPN 网关行→WAF 备行）；前缀规则（一方是另一方前缀→解析截断归 minor）。
- **GPU 显存修复**：fastembed 的 `parallel=False` 触发 onnxruntime worker 线程崩溃、`parallel>1` spawn 进程泄漏占满 T4——统一 `parallel=None`（onnxruntime 内部线程，稳定且不泄漏）；docling 解析后 `torch.cuda.empty_cache()`。
- **测试隔离**：`rag_server/tests/conftest.py` session 级隔离 ConfigStore 保存路径，根除 config.json 被测试污染（base_dir 曾变成 /tmp/rag_test_*）。

### 12.8 embedding 模型实测与 compare_docs 升级（08-16）
- **页眉/页脚处理现状**：pdfplumber/pymupdf 双通道（Y 坐标边界 header/footer_margin_pct=8% + 高频重复行统计，repeat_line_threshold_pct=30%）；docling 靠页眉前缀剥离（段首高频前缀统计）+ 碎尾合并；mineru 依赖模型自带 block 类型分类（跳过 header/page_number/image）。页脚页码普遍被 margin 边界或 block 分类处理，无独立页脚剥离逻辑。
- **embedding 实测**（网络手册 R5-21→R5-22，docling 解析 + 纯规则 LLM）：jina-v2-base-zh GPU 6.3s / bge-small-zh-v1.5 GPU 8.9s / bge-small CPU 44.3s——**三组结果逐条一致**（removed=0/added=1/modified=5/minor=13）。版本对比对 embedding 不敏感，差异主要来自解析后端与吸收逻辑；纯 CPU 环境 bge-small 完全可接受。详见 docs/Embedding模型选型.md §4.1。
- **device_utils 修复**：embedding device=cpu 时显式 `cuda=False`（fastembed 默认 Device.AUTO 抢 GPU，GPU 显存被常驻服务占用时 bfc_arena OOM）。
- **compare_docs 升级**：默认配置与 web 流程对齐（jina-v2-base-zh + docling 页眉剥离/碎尾合并 + device=auto）；新增 `--embedding/--embedding-device/--parse-backend/--parse-device` 参数；重叠度评估 `load_paragraphs` 与 version_compare 共用同一解析配置（避免 auto 路由两阶段不一致，如扫描件判定波动导致 mineru/docling 来回切换）。
