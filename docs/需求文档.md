# 需求文档（Requirements）

> simple_rag — 企业文档检索增强生成（RAG）与版本/一致性管理系统
> 文档版本：v1.0 ｜ 适用代码状态：2026-08 全量重构后

---

## 1. 产品定位

simple_rag 是一个面向**企业多版本文档**场景的 RAG 系统。它把"文档解析 → 入库预审核 → 版本对比 → 对话问答"串联成一条可审计、可追溯的链路，解决企业知识库里最痛的两个问题：

1. **同一主题的文档有多个版本/多个来源，内容彼此矛盾**，检索问答时容易给出错误或不一致的说法。
2. **文档更新频繁**，人工逐字比对版本差异成本高、易遗漏。

系统提供三类核心能力：

- **文档解析**：把 PDF / Word 解析为带定位信息的段落与表格。
- **一致性预审核**：新文档入库前，自动与已有文档做跨文档矛盾检测，辅助人工决策是否入库。
- **版本对比 + RAG 问答**：支持同一文档新旧版本的全量差异罗列，并在问答时自动标注跨文档冲突。

## 2.1 需求、当前实现与未验收项
本文同时保留产品需求和当前代码快照，三者不能混读：FR 条目描述目标行为；“已实现”仅表示当前仓库已有代码路径；“未验收/未接入”表示尚未形成生产 SLA 或端到端保证。当前已实现的关键边界包括：新文档先审核后入库；同完整 SHA-256 内容拒绝重复；同名强制进入 version_diff；逐个 active 文档生成 compare_groups；比较组失败会使顶层审核结果为 error/incomplete 并阻止确认，`parse_qa.incomplete` 不单独阻止确认；确认时才加入全局进程内 FAISS IndexFlatIP；QA 搜索后过滤 inactive；审核报告仅单文件 HTML 且当前不渲染 suspects。任务主要保存在内存，服务重启不能可靠恢复未完成任务。



### 3.1 文档解析（FR-1）

- **FR-1.1** 支持解析 `PDF`、`.docx` 文件（旧版 `.doc` 二进制格式不支持，需先转换为 `.docx`）。
- **FR-1.2** 输出结构化结果：段落（`Paragraph`）与表格（`Table`）。
- **FR-1.3** 每段/每表携带定位信息：页码、章节号、章节标题、来源文件名。
- **FR-1.4** 自动识别页眉/页脚并尽量排除其干扰正文。
- **FR-1.5** 跨页表格自动合并为单个 `Table`。
- **FR-1.6** 表格自动归属到最近的上层章节。
- **FR-1.7** 提供 `to_dict()` / `from_dict()` 序列化能力，作为缓存与落盘的单一数据来源。

### 3.2 版本对比（FR-2）

- **FR-2.1** 输入同一文档的旧版、新版两个文件路径，输出全部变更。
- **FR-2.2** 变更分三类：`added`（新版新增）、`removed`（旧版删除）、`modified`（内容改动）。
- **FR-2.3** 段落级差异：基于语义向量配对（非机械行号对齐），对配对成功的段落做字级 diff。
- **FR-2.4** 表格级差异：跨页/跨表格按表头相似度配对，逐行逐列比较。
- **FR-2.5** 过滤"非实质性变更"（纯标点、空白、格式刷差异），仅保留语义有变化的条目（LLM 辅助判定）。
- **FR-2.6** 每个 `modified` 变更可附带 LLM 生成的变更摘要（如"备份频率从每 4 小时改为每 2 小时"）。

### 3.3 一致性预审核（FR-3）

- **FR-3.1** 新文档上传后，自动解析并嵌入向量。
- **FR-3.2** 对当前 `active` 文档逐个评估并生成 `compare_groups`，按整体相似度从高到低处理；同名文档即使相似度低也强制走 `version_diff`，其他文档按阈值走版本差异或 conflict。
- **FR-3.3** 对差异段落做规则预过滤（章节引用、管理层级、修订表等噪声忽略）。
- **FR-3.4** 对候选差异调用 LLM 判断是否为真正矛盾（而非单纯表述不同）。
- **FR-3.5** 若上传的是已有文档的新版本，额外执行版本对比；确认入库时，有旧主版本的新文档先以 `inactive` 写入，`new_primary` 确认后成为同族唯一 `active`/`primary`，`keep_current` 保留旧主版本，旧版本不自动删除。上传/审核阶段的新文档尚未写入正式文档元数据。
- **FR-3.6** 输出结构化矛盾列表（`Inconsistency`）和与之分开的 `suspects` 疑似项，供管理员在 Web 端确认或拒绝入库；比较组失败会使顶层任务标记为 `error/incomplete` 并阻止 confirm。`parse_qa.incomplete` 只表示解析质量检查未完成，不单独阻止 confirm，但不会写入可复用 review result cache；`parse_qa` 不替代矛盾检测。

### 3.4 RAG 问答（FR-4）

- **FR-4.1** 用户提问，系统检索最相关段落（top_k + 相似度阈值）。
- **FR-4.2** 基于检索内容生成答案，并给出来源引用 `[1][2]`。
- **FR-4.3** 若检索到的段落来自不同文档且存在矛盾，在答案中醒目标注冲突来源。
- **FR-4.4** 支持多轮对话，保留历史上下文（默认上限 20 轮）。
- **FR-4.5** 提供会话列表、历史查看、会话删除、历史重置。

### 3.5 冲突检测（FR-5）

- **FR-5.1** 问答检索后，对跨文档的检索段落做冲突检测。
- **FR-5.2** 检测流程：跨文档 + 非相同文本预过滤 →（带 score 时）score/相似度门控 → LLM 精准确认 → LLM 不可用时回退启发式聚合。
- **FR-5.3** 冲突结果结构：`{point, doc_a_file, doc_a_location, doc_a_says, doc_others:[{file, location, says}]}`。
- **FR-5.4** 提供统一公共入口 `detect_conflicts()`，预审核与问答复用同一实现。

### 3.6 配置与可观测（FR-6）

- **FR-6.1** 支持多 LLM 后端（bedrock / openai）与多模型配置（`llm_profiles`）。
- **FR-6.2** 按用途路由不同模型（qa / pre_review / conflict_detection，`llm_routing`）。
- **FR-6.3** 配置文件优先：rag_server 的 embedding model 从 `config.json` 读取；`SIMPLE_RAG_EMBEDDING_DEVICE` 仅覆盖设备选择。`dtype` 当前只是配置/默认字段，fastembed/ONNX 路径不应用它改变运行精度；`EMBEDDING_MODEL` 仅影响直接无参构造的 standalone `version_diff.Config()` 默认。
- **FR-6.4** 预审核任务提供进度回调与 SSE 实时进度推送；其中 `embedding_progress` 只细化向量阶段，不代表全流程进度，暂停/继续/取消/重跑属于审核控制。
- **FR-6.5** 所有关键步骤记录日志。

## 4. 非功能需求

| 类别 | 需求 |
|------|------|
| 可移植性 | 核心逻辑为纯 Python 包，可在 Linux/macOS/Windows 运行；依赖用 `uv` workspace 管理 |
| 离线能力 | Embedding 模型（BAAI/bge-small-zh-v1.5，基于 fastembed/ONNX）可本地缓存，离线运行；HF 联网可关闭（`HF_HUB_OFFLINE=1`） |
| 可扩展性 | 新增 LLM 后端只需在 `llm_chat/backends/` 实现 `chat()` 接口；新增 prompt 走 `prompts/` 目录 |
| 可测试性 | 每个模块独立 `pytest`；LLM 相关用例可离线跳过或 mock |
| 健壮性 | LLM 调用具备超时、重试和 JSON 解析容错；版本差异过滤失败时保守保留变更，入库预审核任一判断批次失败时整体标记为 `incomplete/error`，不得误报安全 |
| 数据安全 | `config.json`（含密钥/路径）不入库；上传文件按 SHA256 命名，原子写入 |
| 性能 | Embedding 按文件级缓存；向量检索基于 FAISS；大文档瓶颈在 CPU embedding，可切 GPU |

## 5. 典型使用场景

### 场景 A：文档入库前的一致性把关
管理员上传一份新的《IT 运维管理规范》。系统自动与库中已有的《信息安全管理办法》《网络与信息安全管理手册》等做跨文档矛盾检测，发现"备份频率"在两个文档中分别为"每周"与"每天"，提示为矛盾。管理员据此确认是否入库或先修订。

### 场景 B：版本更新比对（历史实验示例，非验收数字）
某手册从一个历史版本修订到另一个历史版本。管理员上传新版本并选择 `coexist`，系统展示按当前解析和配置得到的差异分类；确认时可用 `keep_current` 保留旧主版本，或用 `new_primary` 切换新版本。过去某批实验曾记录过具体条数，但该数字受样本、解析后端和配置影响，不是产品 SLA 或固定验收标准。

### 场景 C：带冲突标注的问答
用户问"我们的备份频率是多少？"问答引擎同时检索到文档 A（每周）与文档 B（每天），检测到矛盾后在答案中醒目标注两处来源的冲突，提示"以最新版本或上级文档为准"。

## 6. 范围与边界

**在范围内**
- 结构化/半结构化企业文档（PDF / `.docx`）的解析与比对（旧版 `.doc` 二进制格式不在支持范围，需转换为 `.docx`）。
- 跨文档、跨版本的中文文本矛盾与差异识别。
- 基于检索的问答与冲突标注。

**不在范围内（当前版本）**
- 图片独立 OCR 能力（扫描件 PDF 可通过 auto 路由或显式 MinerU 后端解析）。
- 文档的自动修订建议生成（仅检测，不自动改写）。
- 多语言文档混合比对（当前以中文为主）。

## 7. 当前实现边界与未验收项

- 扫描件解析不是独立 OCR 产品：当前通过 `doc_parser` 的 `auto` 或显式 MinerU 后端尝试 OCR/视觉解析，质量依赖样本和运行时依赖；没有独立 OCR SLA。
- 版本回滚/审核控制：可用 `keep_current` 保留旧主版本、`new_primary` 切换主版本，也可通过文档管理接口手工设置历史版本为 primary；旧版本不自动删除。审核支持 pause/resume/cancel/rerun/reject/confirm，但权限控制、审批人审计和多租户隔离尚未实现。
- `parse_qa` 默认关闭，是可选解析质量旁路；它的报告和 `incomplete` 与 compare group 的确定性矛盾/失败分开。
- 报告当前只有 `report.html` 单文件 HTML，且不渲染 `suspects`；没有已实现的 PDF/JSON/CSV 导出承诺。
- 清空知识库不等于删除 chat history、logs 或上传目录；服务重启也不能可靠恢复未完成的内存任务。AWS/OpenSearch/DynamoDB/Aurora/Keycloak/S3/Secrets Manager 仍是目标方案，不是当前验收范围。
- 本文没有为全流程、性能、解析准确率或测试通过数提供固定 SLA；应以当前样本、配置、区域、设备和实际运行结果验收。
