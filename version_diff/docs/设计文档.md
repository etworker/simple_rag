# version_diff 设计文档

> 文档差异检测引擎 — 语义配对 + 字级 diff + 规则预过滤 + LLM 矛盾判定

---

## 1. 设计目标

为 `simple_rag` 项目提供文档差异检测能力：

- **跨文档矛盾检测**：新文档入库前，自动与已有文档逐段对比，发现矛盾即标记
- **版本对比**：同一文档新旧版本，列出全部 added/removed/modified 变更
- **问答冲突检测**：RAG 检索结果中是否存在矛盾描述

核心难点与解法：

| 难点 | 解法 |
|------|------|
| 段落配对：哪两段说的是同一件事？ | 语义向量（fastembed/ONNX + FAISS） |
| 差异判定：哪些差异是真正矛盾？ | 规则预过滤 + LLM 确认 |
| 噪声干扰：修订日期/版本号等 | 可配置正则剥离 + 内置兜底模式 |
| 表格对比：行列增减/内容修改 | 表头配对 + 列对齐 + 行级 diff |
| LLM 不稳定 | JSON 解析重试 + 启发式回退 |

## 4. DiffEngine — 主入口

### 4.1 pre_review 流程

```
pre_review(filepath)
  │
  ├─ 1. 解析新文档 (doc_parser.parse)
  ├─ 2. 计算新文档 embedding (VectorStore.get_or_compute)
  ├─ 3. 跨文档语义检索 (FAISS top-K)
  │     → candidates = [(para_a, para_b, similarity), ...]
  ├─ 4. 字级 Diff (matcher.compute_diff)
  │     → diff_items = [TextDiffItem, ...]
  ├─ 5. 规则预过滤 (prefilter.batch_pre_classify)
  │     → 排除编号/元数据/层级差异
  ├─ 6. LLM 矛盾判定 (judge.filter_diffs)
  │     → 分批发送，每批 N 对，LLM 返回 JSON
  └─ 7. 封装 DiffResult
```

**增量回调**：`on_candidates` / `on_judge_batch` 允许前端实时显示进度。

### 4.2 version_compare 流程

```
version_compare(old, new)
  │
  ├─ 1. 解析新旧文档
  ├─ 2. 语义配对 (matcher.pair_paragraphs)
  │     → 贪心配对：按相似度排序，每段只配一个
  ├─ 3. 逐对比较
  │     ├─ 配对成功 → modified
  │     ├─ 旧版有新版无 → removed
  │     └─ 新版有旧版无 → added
  ├─ 4. 表格对比 (table_diff.compare_tables)
  ├─ 5. 实质性变更过滤
  │     ├─ 规则：修订日期/版本戳/跟踪表行 → minor_changes
  │     └─ LLM：批量判断 modified 是否实质性变更
  └─ 6. 封装 VersionDiffResult
```

### 4.3 check_conflicts 流程

```
check_conflicts(passages)
  │
  └─ 委托 conflict.detect_conflicts
     ├─ 1. 跨文档 + 非相同文本预过滤
     ├─ 2. LLM 确认 (judge_pairs)
     └─ 3. LLM 不可用 → 启发式回退
```

## 5. 核心组件

### 5.1 matcher — 段落配对 + 字级 diff

**配对策略**：FAISS top-K 检索 → 按相似度降序贪心配对（每段只配一个）。

**diff 策略**：
- 中文文本：逐字符 diff（`list(text)`）
- 英文文本：逐词 diff（`text.split()`）
- 使用 `difflib.SequenceMatcher` 计算 opcodes

### 5.2 vectorstore — 向量缓存

- 按"段落内容哈希 + 段落数 + 配置哈希"作为缓存 key
- 同一文档重复调用时零计算（直接读 FAISS index + embeddings）
- 配置变化时缓存自动失效（哈希变化）

### 5.3 judge — LLM 矛盾判定

```
filter_diffs(diff_items, llm_config, judge_config)
  │
  ├─ 1. 规则预过滤 (prefilter.batch_pre_classify)
  │     → 排除：仅编号差异 / 元数据差异 / 层级名称差异
  ├─ 2. 剩余项分批发送 LLM
  │     ├─ batch_size = 5（可配置）
  │     ├─ 每批构造 prompt：{count} 对段落
  │     └─ LLM 返回 JSON：[{index, inconsistent, point, doc_a_says, doc_b_says}]
  ├─ 3. 解析 LLM 结果，标记 inconsistent 项
  └─ 4. LLM 不可用 → 全部保留（宁滥勿缺）
```

### 5.4 prefilter — 规则预过滤

| 规则 | 说明 |
|------|------|
| 仅编号差异 | "1.1" vs "1.2"，文本相同仅编号变 |
| 元数据差异 | 修订日期、版本号、页码等 |
| 层级名称差异 | "二级" vs "三级"，其余相同 |
| 纯格式差异 | 空白/标点差异 |

### 5.5 table_diff — 表格对比

```
compare_tables(old_tables, new_tables)
  │
  ├─ 1. 表格配对：按表头内容相似度（Jaccard）
  ├─ 2. 列对齐：按列名模糊匹配
  ├─ 3. 行对齐：按首列关键字
  └─ 4. 逐单元格比较，输出 VersionChange
```

### 5.6 normalization — 文本归一化

- `normalize_text`：统一空白/全角半角/不可见字符
- `strip_revision_noise`：剥离修订日期/版本号/页码
- `strip_configured_noise`：按配置正则剥离
- `is_tracking_table_row`：识别跟踪表行

### 5.7 noise — 跨文档版式噪声过滤

对比不同体例的文档时（如二级手册 vs 三级手册），目录/记录清单/页码占位等版式差异会被误判。`CrossNoiseFilter` 用内置模式 + 可配置超参数过滤。

### 5.8 llm_util — LLM 调用工具

```python
call_llm_json(prompt, llm_config)
  │
  ├─ 调用 llm_chat.ask_once_with_config(llm_config, prompt)
  ├─ 正则提取 JSON 数组 [..]
  ├─ json.loads → list[dict]
  └─ 失败重试（指数退避，默认 2 次）
```

## 6. 配置

### Config dataclass

```python
@dataclass
class Config:
    embedding: dict  # 模型/设备/精度
    llm: dict  # provider/model/区域/密钥/超时
    diff: dict  # 阈值/top_k/batch/噪声过滤
    judge: dict  # prompt 覆盖
    cache: dict  # 向量缓存目录
```

### LLM 配置归一化

`Config.from_dict` 调用 `llm_chat.resolve_llm_config` 归一化 LLM 配置，支持两种形态：
- 单配置：`{"provider": "openai", "model": "..."}`
- Profile 引用：`{"profile": "glm", "llm_profiles": {...}, "routing": {...}}`

## 7. 数据模型

### DiffResult（预审核结果）

```python
@dataclass
class DiffResult:
    inconsistencies: list[Inconsistency]
    total_candidates: int    # 候选对数
    rule_filtered: int       # 规则过滤数
    llm_judged: int          # LLM 判断数

    @property
    def is_safe(self) -> bool  # 无矛盾 → True
    def report(self) -> str    # Markdown 报告
```

### VersionDiffResult（版本对比结果）

```python
@dataclass
class VersionDiffResult:
    changes: list[VersionChange]  # 实质性变更
    minor_changes: list[VersionChange]  # 被过滤的细微变更
    old_paragraph_count: int
    new_paragraph_count: int
```

### VersionChange

```python
@dataclass
class VersionChange:
    change_type: str  # "modified" | "added" | "removed"
    section: str  # 章节
    location: str  # 位置
    old_text: str
    new_text: str
    summary: str  # 变更摘要
    similarity: float  # 段落相似度
    category: str  # "content" | "tracking_table" | "metadata"
```

## 8. 设计决策

### 为什么用 FAISS 而非全量矩阵？

- 文档量大时，N×M 全量矩阵计算慢且内存高
- FAISS top-K 检索 O(N·log M)，且支持 GPU 加速
- 向量已归一化，内积 = 余弦相似度

### 为什么贪心配对而非匈牙利算法？

- 段落配对不需要全局最优，贪心按相似度降序已足够
- 匈牙利算法 O(n³) 对大文档太慢
- 实际效果差异不大

### 为什么规则预过滤 + LLM 而非纯 LLM？

- 纯 LLM 成本高、慢，且对编号/元数据差异容易误判
- 规则预过滤先排除明显噪声，减少 LLM 调用量
- LLM 只判断"可能有矛盾"的候选对

### 为什么 LLM 不可用时全部保留？

- 宁滥勿缺：漏报矛盾比误报矛盾风险更大
- 保留的项仍可由人工审核
- LLM 不可用可能是临时网络问题，下次调用可能恢复
