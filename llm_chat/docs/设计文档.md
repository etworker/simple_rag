# llm-chat 设计文档

> 轻量多后端 LLM 多轮对话管理 — Bedrock Converse / OpenAI 兼容

---

## 1. 设计目标

为 `simple_rag` 项目中的各模块（`rag_server` / `version_diff` / `demo`）提供统一的 LLM 调用层：

- **零外部依赖**：仅用标准库 `urllib`，无需 `boto3` / `openai` SDK
- **多后端切换**：Bedrock Converse API 和 OpenAI 兼容 API 通过同一接口调用
- **多轮对话管理**：自动维护历史、截断、错误恢复
- **配置复用**：命名 Profile + 路由机制，避免各模块各自硬编码 LLM 配置

核心难点与解法：

| 难点 | 解法 |
|------|------|
| 不同后端 API 格式差异 | 抽象 `BaseHTTPBackend` 基类，子类只实现 `_parse_response` |
| API Key 跨后端误用 | 分级解析：显式 `api_key` > 环境变量 `api_key_env` |
| 429 限流 / 5xx 错误 | `retry_http` 指数退避重试，异常属性驱动（不解析 message） |
| 多模块 LLM 配置重复 | `profile.py` 统一 profile + routing 解析 |
| 对话历史无限增长 | `max_history` 轮数截断，保留最近 N 轮 |

## 4. ChatSession — 多轮对话

```python
class ChatSession:
    def __init__(self, system_prompt, backend, model, max_history, **kwargs)
    def ask(self, question: str, context: str = "") -> str
    def reset(self)
    def get_history(self) -> list[dict]
```

### 调用流程

```
ask(question, context)
  │
  ├─ 1. 构建 user 消息（有 context 则拼接参考资料）
  ├─ 2. 追加到 self.messages
  ├─ 3. 构建 conversation = [{role, content}, ...]
  ├─ 4. 调用 backend.chat(conversation, system_prompt)
  │     ├─ 成功 → 追加 assistant 消息到历史
  │     └─ 失败 → RuntimeError 直接抛出（不污染历史）
  ├─ 5. 截断历史（保留最近 max_history 轮 = max_history * 2 条消息）
  └─ 6. 返回 answer
```

### 错误处理策略

| 异常类型 | 处理 |
|---------|------|
| `RuntimeError`（API Key 缺失等） | 直接抛出，让上层处理 |
| 其他异常 | 记录日志，返回 `"[错误] ..."` 字符串 |
| 调用失败 | 不写入历史，避免错误文本污染多轮上下文 |

## 4.1 ask_once / ask_once_with_config — 单次调用

`ask_once` 是无状态一次性调用，不保留对话历史，适用于分类/判断/摘要等任务。

`ask_once_with_config` 从配置字典中解析后端和模型参数，消除调用方手写字段透传的样板代码：

```python
def ask_once_with_config(llm_config: dict, prompt: str, system_prompt: str = "") -> str:
    from llm_chat import ask_once  # 函数内 import，使 mock.patch 仍能拦截

    cfg = dict(llm_config)  # 浅拷贝，避免修改入参
    backend = cfg.pop("provider", "") or DEFAULT_BACKEND
    model = cfg.pop("model", "") or DEFAULT_MODELS.get(backend, "")
    return ask_once(prompt, system_prompt=system_prompt, backend=backend, model=model, **cfg)
```

**设计要点**：
- `provider` → `backend`：配置字典用 `provider` 字段名（与 `rag_server` 的 `config.json` 一致），映射为后端名
- `model` 单独 `pop`：避免被当作 `**kwargs` 透传给后端（后端 `__init__` 已有 `model` 参数）
- 函数内 `import`：使 `mock.patch("llm_chat.ask_once")` 仍能拦截实际调用
- 余字段透传：`base_url` / `api_key` / `api_key_env` / `region` / `max_tokens` / `timeout` 等直接传给后端

## 5. 后端实现

### 5.1 BaseHTTPBackend — 公共基类

```python
class BaseHTTPBackend:
    def _init_common(self, defaults, api_key_env, api_key, ...)
    def _resolve_key(self) -> str    # 显式 key > 环境变量
    def _send(self, req, parse_fn) -> str  # HTTP 请求 + 错误处理
```

**API Key 分级解析**：

```python
def _resolve_key(self):
    if self.api_key:  # 显式传入优先
        return self.api_key
    return os.environ.get(self.api_key_env, "")  # 回退到环境变量
```

**HTTP 错误处理**：异常挂属性，`retry.py` 读属性判断是否重试：

| 错误 | 属性 | 是否重试 |
|------|------|---------|
| 401 认证失败 | `status_code=401` | 否 |
| 429 限流 | `status_code=429` | 是 |
| 5xx 服务端错误 | `status_code=500` | 是 |
| 网络错误 | `is_network_error=True` | 是 |

### 5.2 BedrockBackend — Bedrock Converse API

```
POST https://bedrock-runtime.{region}.amazonaws.com/model/{model}/converse
Authorization: Bearer {key}

请求体:
{
  "messages": [{"role": "user", "content": [{"text": "..."}]}],
  "system": [{"text": "..."}],           ← 顶层 system 字段
  "inferenceConfig": {"maxTokens": 2048}
}

响应体:
{
  "output": {"message": {"content": [{"text": "..."}]}}
}
```

### 5.3 OpenAIBackend — OpenAI 兼容 API

支持两种端点：

**`/chat/completions`（默认）**：

```
POST {base_url}/chat/completions
{
  "model": "...",
  "messages": [{"role": "system", ...}, {"role": "user", ...}],
  "max_tokens": 2048
}
```

**`/responses`)``（`endpoint="responses"`）**：

```
POST {base_url}/responses
{
  "model": "...",
  "input": [{"role": "user", "content": "..."}],
  "instructions": "...",           ← system 提示放在 instructions
  "max_output_tokens": 2048
}
```

响应解析兼容两种格式：`choices[0].message.content` 和 `output[].content[].text`。

## 6. retry_http — HTTP 重试

```python
def retry_http(fn, max_retries=3, backoff=2.0):
    for attempt in range(max_retries + 1):
        try:
            return fn()
        except RuntimeError as e:
            should_retry = is_net or status == 429 or 500 <= status < 600
            if not should_retry or attempt == max_retries:
                raise
            time.sleep(backoff**attempt)
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `max_retries` | 3 | 最大重试次数（不含首次） |
| `backoff` | 2.0 | 退避基数（第 n 次等 `backoff^n` 秒） |

重试判定依赖异常属性（`status_code` / `is_network_error`），不解析 message 字符串。

## 7. Profile 配置机制

### 7.1 数据结构

```python
llm_profiles = {
    "glm": {
        "provider": "openai",
        "model": "gpt-5.6-luna",
        "base_url": "https://...",
        "api_key_env": "OPENAI_API_KEY",
    },
    "cheap": {
        "provider": "bedrock",
        "model": "zai.glm-4.7-flash",
    },
}

llm_routing = {
    "version_compare": "glm",  # 版本对比用 glm
    "qa": "glm",  # 问答用 glm
    "draft": "cheap",  # 草稿用 cheap
}
```

### 7.2 解析流程

```
resolve_llm_profile(profiles, routing, "version_compare")
  │
  ├─ 1. name = routing["version_compare"] → "glm"
  ├─ 2. return profiles["glm"]（深拷贝）
  │
  └─ 回退：如果 routing 中没有该 use_case → 取第一个 profile
```

```
resolve_llm_config(llm)
  │
  ├─ llm 无 "profile" 键 → 原样返回（单配置形式）
  │
  └─ llm 有 "profile" 键 → 按 profile 名从 llm_profiles 中解析
     （兼容 routing 机制）
```

### 7.3 使用示例

```python
# version_diff 引擎中
from llm_chat import resolve_llm_config

llm_cfg = resolve_llm_config(config.get("llm"))
session = ChatSession(
    backend=llm_cfg.get("provider", "bedrock"),
    model=llm_cfg.get("model"),
    base_url=llm_cfg.get("base_url"),
    api_key=llm_cfg.get("api_key"),
    api_key_env=llm_cfg.get("api_key_env"),
)
```

## 9. 设计决策

### 为什么不用 boto3 / openai SDK？

- **减少依赖**：`boto3` 重达 100+ MB，`openai` SDK 也在持续变化
- **Bedrock Converse API** 支持原生 Bearer Token，不需要 SigV4 签名，用 `urllib` 即可
- **OpenAI 兼容接口** 本身就是简单 HTTP POST，SDK 反而增加抽象层

### 为什么异常挂属性而非子类化？

- `retry_http` 只需判断"是否重试"，读属性比 `isinstance` 判断更简洁
- 避免定义 `RateLimitError` / `ServerError` / `NetworkError` 等异常类层次
- `RuntimeError` + `status_code` 属性足以表达所有需要的信息

### 为什么失败不写入历史？

- 错误消息（如 `"[错误] LLM 调用失败: ..."`）写入历史后，后续轮次会把错误文本当作上下文
- 这会导致 LLM 困惑或产生连锁错误
- 失败时只抛异常或返回错误字符串，不追加到 `self.messages`
